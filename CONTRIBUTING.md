# Разработка

Нужны Go 1.26+, Node.js 22.12+ и npm; для GitHub CI используется Node.js 24. Сборка frontend обязательна перед Go-проверками, поскольку `web/dist` встраивается в бинарник.

```sh
make frontend
make test-race vet frontend-check packaging-check fixtures-check
make build proxy-build capture-build
```

Эти проверки не запускают игровые сервисы и не заменяют аварийную или нагрузочную приёмку на выделенном Linux-хосте. Интеграционные сценарии, изменяющие Docker, порты или данные, выполняйте только на отдельном стенде по [инструкции тестирования](docs/testing.md).

Нативные Linux-архивы собираются командой `make native-release VERSION=0.1.0-dev`. Формат пакета, GitHub Actions и безопасное повторение сборки описаны в [native-release.md](docs/native-release.md). Интеграционный `native_systemd_smoke.py` устанавливает собственные службы только на свежем ephemeral GitHub runner с явным opt-in; на игровом хосте он не запускается.

Для изменений поведения добавляйте проверку существенной регрессии и обновляйте соответствующие контракт, ТЗ и матрицу приёмки. В PR укажите проблему, итоговое поведение, выполненные проверки и ограничения.

Для каждого изменения создавайте отдельную ветку, например `feat/...`, `fix/...` или `docs/...`, и открывайте Pull Request в `main`. Обычная разработка не использует прямые push в `main`.

Перед коммитом подготовьте индекс и проверьте именно публикуемые файлы:

```sh
git add .
make publication-check
git diff --cached --stat
git diff --cached
```

Проверка публикации — дополнительный барьер; просматривайте diff самостоятельно. Не добавляйте секреты, рабочее состояние, внешние исходники и сырые локальные отчёты через `git add -f`. Публичный синтетический `tests/real-services/bank.env` является тестовым fixture.

Код проекта публикуется под [MIT](LICENSE). Зависимости и внешние игровые сервисы сохраняют свои лицензии; фиксация upstream и особенности адаптации описаны в [профилях SibirCTF](docs/real-services.md).
