# Пассивный захват TCP/UDP: отдельный профиль Linux

Профиль `compose.capture.yaml` добавляет два контейнера: `packet-capture` читает
пакеты в сетевом пространстве Linux-хоста; `packet-store` сохраняет их в отдельной
SQLite-базе. HTTP Proxy/WAF для этого не требуется. Прокси продолжает работать
независимо от доступности захвата и архива.

Профиль рассчитан на Linux Docker Engine. В этой итерации проверены Go-код,
искусственные кадры, SQLite, HTTP/Unix API и структура упаковки локально.
Запуск контейнеров с настоящим `CAP_NET_RAW`, потеря пакетов под нагрузкой и
проверки на целевой VM пока отложены.

## Подготовка

Определить точные имена observation interfaces (Docker bridge, bridge-member veth либо host/lo для game publication), через которые идут игровые
сервисы, например `docker0` или `br-0123456789ab`. Каждый интерфейс задаётся
отдельным аргументом; маски не принимаются. `lo` допускается только для предложенных executor игровых публикаций с защитой management ports. Список становится границей
настроек панели. Включение захвата дополнительно требует совпадения bridge с
актуальным Docker endpoint зарегистрированного компонента.

```sh
sudo python3 scripts/capture-bootstrap.py \
  --root /srv/ctfm-capture \
  --interface br-0123456789ab
```

Скрипт создаёт **новый** каталог. Существующие установки и `executor.json` он
не изменяет. Начальная политика выключена, `snaplen=0`; сырые сокеты захвата
до включения политики не открываются. Создаются три разных случайных секрета
с отдельными копиями для владельцев файлов: control, ingest и read. Секреты
имеют режим `0600`, в вывод не попадают.

Содержимое `/srv/ctfm-capture/executor_capture_patch.json` нужно добавить как
поле `capture` в действующий `executor.json`. Остальные поля конфигурации
сохраняются. В основном Compose-проекте executor должен получить пять bind
mount из сгенерированного `executor-capture.override.yaml`:

- `policy` с записью для публикации утверждённой политики;
- `capture-control` и `packets-control` только для чтения;
- два файла executor-токенов только для чтения.

Например, к уже используемому набору Compose-файлов основного проекта добавить
`-f /srv/ctfm-capture/executor-capture.override.yaml`, затем пересоздать executor
после проверки объединённой конфигурации. Для стандартного пути есть также
`compose.capture.executor.yaml`; параметр `CTFM_CAPTURE_ROOT` и пути внутри
`executor.json` должны совпадать. Dashboard эти каталоги и секреты не получает.

Затем отдельный профиль можно собрать и запустить на подготовленном Linux-хосте:

```sh
docker compose --env-file /srv/ctfm-capture/compose.env \
  -f compose.capture.yaml config
docker compose --env-file /srv/ctfm-capture/compose.env \
  -f compose.capture.yaml up -d --build
```

Это отдельный проект `ctfm-packets`. Команды выше приведены для последующего
развёртывания; текущие локальные проверки их не запускали.

## Права и сетевые границы

`packet-capture` работает как UID 0, со сброшенными capabilities и единственным
`NET_RAW`. `NET_ADMIN`, privileged mode, host PID, Docker socket, IPC ядра
executor и игровые каталоги ему не выдаются. Корневая ФС доступна только для
чтения, политика и токены монтируются только для чтения. Writable mount нужен
только для отдельного control Unix socket, также есть ограниченный tmpfs.

`packet-store` работает как UID/GID 10005 без capabilities, в отдельной private
bridge-сети. Единственный опубликованный TCP-порт — `127.0.0.1:9804`, только для
ingest и health. Метаданные, сырые байты и PCAP читаются через приватный Unix
socket с отдельным read-токеном; ingest-токен читать их не может. Управление
коллектором — отдельный socket и токен, health доступен на loopback-порту 9803.
Все data API требуют авторизацию. Права пользователя, повторная проверка сессии
и аудит чувствительных чтений проверяются в dashboard; executor связывает настройки с проверенным runtime.

## Хранение и ограничения

По умолчанию физический бюджет SQLite и rollback journal — 256 MiB. Логический
бюджет записей — 64 MiB суммарно и до 64 MiB на сервис, срок — 60 минут, максимум
100 000 записей. Достижение любого лимита удаляет старые записи; неоднозначный
пакет учитывается в квоте каждого кандидата. SQLite дополнительно ограничен
через `max_page_count`; WAL не используется. Резерв свободного места — 1 GiB
плюс запас для журнала. Ошибка записи или исчерпание резерва останавливает новые
записи до перезапуска архива, а сохранившиеся записи остаются доступны.

На контейнер заданы 256 MiB RAM и 0.5 CPU. Это ограничения профиля, а не
подтверждённая пропускная способность. Очередь коллектора ограничена 256
пакетами; перегрузка и ошибки ingest учитываются как потери. Счётчики относятся
к текущему запуску, неизвестные потери ядра явно помечаются. После ротации или
смены эпохи API возвращает признак разрыва. Полноту захвата без нагрузочной
проверки на целевом хосте обещать нельзя.

PCAP — классический Ethernet формат, максимум 10 000 пакетов и 8 MiB на экспорт;
лимиты могут быть уменьшены запросом. Экспорт выполняется в памяти без временных
файлов. Порядок соответствует последовательности захвата; настоящие повторные
передачи TCP сохраняются. Для урезанного пакета `incl_len` равен сохранённым
байтам, `orig_len` — размеру кадра. В режиме metadata-only `incl_len=0`: PCAP
сохраняет время и исходный размер, но протокол по таким данным не декодируется.

Захват остаётся пассивным: он не перенаправляет и не блокирует TCP/UDP.
Добавлены bounded TCP-потоки и plaintext HTTP/2/gRPC decoder; TLS visibility включается отдельной HTTPS/2 termination. Расшифровки TLS passthrough/QUIC/keylogs нет.
Payload показывается как безопасные hex/ASCII байты; зашифрованные данные
остаются зашифрованными. WAF продолжает применять правила к HTTP-трафику.

## Включение через панель

Открыть «Трафик → Пакеты → Захват» под Admin. Выбрать предложенные цели,
указать PPS и режим metadata-only либо явный snaplen, затем проверить preview
и подтвердить digest. Политика применяется асинхронно; смотреть applied revision
и running, а не только желаемую настройку enabled. Поиск целей не открывает
произвольных соединений к игре и не меняет её порты.

Текущий профиль требует до 8 сверенных bridge-сетей application-компонента,
private контейнерные IP и явные TCP/UDP ports из сверенного runtime. Host/overlay network mode и неподтверждённые интерфейсы отображаются как недоступные.
Контейнерный адрес выбран как единственная точка для target: host/NAT leg
одновременно не включается. Между несколькими bridge интерфейсами всё ещё
возможны отдельные наблюдения одного соединения; TCP byte ranges объединяются с сохранением provenance; исходные packet observations и UDP-дубликаты не удаляются по эвристике.

Единственный worker executor продлевает lease на 10 секунд каждые 2 секунды
после проверки runtime. Перед изменением контейнеров, компенсацией или переносом
портов захват приостанавливается. После изменения container/network/interface
identity требуется свежий preview. При рестарте collector старый enabled-файл
не запускает сокеты: executor должен опубликовать заново проверенный файл уже
после старта collector. Остановка executor приводит к истечению lease, без
влияния на игровые соединения. Внешняя смена Docker IP обнаруживается проверкой
карты или истечением последнего lease, мгновенная реакция не гарантируется.

Raw bytes и PCAP доступны только с `sensitive_access`; просмотр метаданных
доступен всем аутентифицированным ролям. Настройка capture — Admin. HTTP WAF
не блокирует произвольный TCP/UDP от включения этой вкладки.

Если выбраны оба конца пакета между сервисами, его direction отмечается
`ambiguous`. В таблице и фильтре есть отдельный вариант; фильтры ingress/egress
показывают только наблюдения с однозначным направлением, без назначения
направления одному из нескольких кандидатов.

## Новые точки и анализ

Capture targets теперь содержат canonical point group: для одного target выбирают bridge, подтверждённый член bridge `veth` либо host-publication leg. Veth-membership не выдаётся за доказательство конкретного container peer. Адреса/порты выводятся из private Docker runtime и адресов одобренных интерфейсов; браузер их не задаёт. Для нескольких Docker-сетей доступны bridge/veth, host leg предлагается только при единственном однозначном NAT target.

Host ports 22, 2222, 2375/2376, 8765, 18765 и 9801–9804 исключены. Для нестандартных management ports передайте bootstrap `--protect-host-port <port>`; список только расширяет защиту. На verified game container endpoint порт22 сам по себе допустим. Один target может использовать несколько host publications, но не одновременно host и container leg.

«Трафик → TCP-потоки / gRPC» работает с архивом без дополнительных raw capabilities/контейнера. По умолчанию bytes не записываются: для stream payload нужно явно выбрать snaplen. Descriptors подключаются через preview/digest/confirm в панели с pin к версии, хранятся в private packet archive. [Использование, API и ограничения](traffic-analysis.md).
