# Метрики хоста и сервисов

Executor собирает метрики раз в 5 секунд независимо от открытых вкладок. История хранится в RAM за последние 60 минут и ограничена 721 точкой на ряд, включая границу окна. Перезапуск executor очищает историю; API возвращает время её начала. Отсутствие данных, ошибка источника и устаревшее измерение не заменяются нулём. UI разрывает линию при промежутке более 1,8 интервала (9 секунд) и смене container ID. Backend отмечает срез устаревшим после трёх интервалов (15 секунд).

В интерфейсе есть отдельная страница «Метрики хоста», доступная без регистрации игровых сервисов. Вкладка метрик сервиса показывает также его контейнеры. По умолчанию графики отображают последние 15 минут; переключатель позволяет выбрать 60 минут. API отдаёт последнюю точку всех компонентов и часовую историю выбранного компонента, чтобы ответ оставался ограниченным по размеру.

## Источники хоста

При установке на Linux Docker host включите сбор явно:

```sh
sudo python3 scripts/compose-bootstrap.py --root /srv/ctf-manager --host-metrics
```

Для существующей установки сначала проверьте `--dry-run`, затем повторите ранее использованные параметры с `--host-metrics --replace-config` и пересоздайте executor через Compose. Каталоги discovery/workspace и опциональный Docker storage root должны соответствовать действующей установке.

Bootstrap добавляет только executor следующие отдельные bind mounts с `read_only: true` и `create_host_path: false`:

| Источник на Linux Docker host | Назначение в executor | Показатели |
|---|---|---|
| `/proc/stat` | `/run/ctf-manager-host/stat` | CPU по разности счётчиков |
| `/proc/meminfo` | `/run/ctf-manager-host/meminfo` | RAM и swap |
| `/proc/loadavg` | `/run/ctf-manager-host/loadavg` | Load average 1/5/15 минут |
| `/proc/uptime` | `/run/ctf-manager-host/uptime` | Время работы Linux host |
| `/proc/1/net/dev` | `/run/ctf-manager-host/net-dev` | Счётчики интерфейсов сетевого namespace host PID 1 |

Mounts разрешаются на стороне Docker daemon. В Docker Desktop/OrbStack хостом этих метрик является Linux VM, а не macOS. `/proc/net/dev` контейнера показывает его собственный network namespace и не используется как источник сети хоста. Runtime проверяет procfs и read-only mount каждого источника. При неподтверждённом или недоступном источнике соответствующие значения недоступны. Включение сбора не добавляет privileged, host PID/network namespaces, mount всего `/proc`, `/sys` или `/`.

Смысл Linux-счётчиков описан в [документации procfs](https://www.kernel.org/doc/html/latest/filesystems/proc.html) и [документации сетевой статистики](https://www.kernel.org/doc/html/latest/networking/statistics.html). Host CPU подписан как процент суммарной мощности всех ядер, container CPU — как процент одного ядра. RAM использует доступную память `MemAvailable`; сетевые счётчики виртуальных интерфейсов могут учитывать один пакет несколько раз и не считаются уникальным внешним трафиком хоста.

Свободные байты и inode измеряются на уже разрешённых файловых системах executor state, discovery/workspace roots и отдельно разрешённого Docker storage root. Весь корень хоста ради `statfs` не монтируется. Недоступные inode отображаются отдельно от нулевого остатка. Число путей и интерфейсов ограничено; ограничения показываются в ответе, а не скрываются бесконечным накоплением.

Жёсткие бюджеты: 128 рядов сервисов, 128 контейнеров за цикл, 16 путей файловых систем и 128 сетевых интерфейсов. Ошибка или исчерпание бюджета показываются явно. Для native development-профиля файловая система имеет scope `local_executor`, для контейнерных путей без подтверждённых host proc mounts — `executor_mounts`; эти наблюдения не объявляются полными метриками Docker host.

Для контейнеров также доступны block I/O, число процессов и доступные лимиты, счётчик рестартов и текущий флаг `OOMKilled`. Последний берётся из Docker inspect и может сбрасываться при рестарте. Отдельная подписка Docker events сохраняет OOM/restart/die/start/destroy в SQLite: последние 10 000 событий глобально, до 200 в ответе сервиса. После перезапуска executor выполняет ограниченный replay с дедупликацией. При отключении возможны пропуски из-за ограниченного буфера Docker; UI показывает состояние подключения и эту границу полноты. Событие start само по себе не доказывает автоматический restart.

## API и ограничения

- `GET /api/metrics/host` — доступен любому вошедшему пользователю, как и метрики сервисов.
- `GET /api/services/{id}/metrics` — последний срез всех компонентов и история выбранного по умолчанию компонента.
- `GET /api/services/{id}/metrics?component=app` — история только зарегистрированного компонента; произвольные пути и дополнительные параметры не принимаются.

Эти маршруты dashboard обращаются к фиксированному Unix API executor. Вызов API не запускает дополнительный сбор Docker stats на каждый запрос. История не является архивом наблюдений и не включается в backup состояния панели. После паузы или сбоя отсутствующие точки не достраиваются. Длительная история, downsampling и постоянное хранилище метрик остаются за пределами MVP.

Нагрузочный прогон и фактические ограничения среды фиксируются в [матрице приёмки](progress.md). Успех короткого теста или прогона на другой VM не подтверждает цели опорного стенда §17.3 ТЗ.
