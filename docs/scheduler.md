# Очередь, приоритеты и ограничения параллелизма

Executor хранит задания и конфликты ресурсов в SQLite. Закрытие страницы не отменяет работу. Одна изменяющая операция сервиса, Compose project или пересекающихся путей не выполняется одновременно с конфликтующей операцией; восстановление сохраняет прежние locks до подтверждённого результата.

## Настройка

Локальная root-owned конфигурация executor принимает независимые ограничения:

```json
"scheduler": {"builds": 1, "copies": 1, "switches": 1}
```

Каждое значение — от 1 до 4; отсутствующее/нулевое поле старой конфигурации выбирает 1. Bootstrap принимает `--max-builds`, `--max-copies`, `--max-switches` с теми же пределами. По умолчанию одновременно активны максимум одна сборка, одна подготовка/загрузка и одно переключение. Увеличение switching limit требует отдельной проверки нагрузки и жизненного цикла конкретного хоста. Общий предел — 12 jobs; одного jobs на сервис по-прежнему достаточно для блокировки конфликта.

| Группа | Операции |
|---|---|
| builds | Build |
| copies | Prepare, Fetch из Git, Snapshot, Snapshot → кандидат |
| switches | Start, Stop, Restart, Deploy, Rollback |

Новые Recover имеют приоритет, затем выбираются queued Rollback, Stop и остальные задания по времени создания. Уже выполняющийся критический шаг не прерывается ради более приоритетного задания. Explicit Recover сериализуется с активными switching jobs, но подготовленные сборки и Git-загрузки могут завершаться параллельно. Если нужная группа занята, независимые группы продолжают работу.

Задание остаётся `queued`, пока нельзя получить artifact gate и все durable resource locks. Его execution timeout начинается после фактического старта. Ожидание свободного artifact gate не расходует execution timeout. Отмена queued-задания не запускает его ради обработки отмены.

## Защищённые участки

Параллельность используется в долгих ожиданиях: Docker Build CLI, Git network download, прогрев и локальные проверки. Копирование файлов, проверка и выделение места, публикация snapshots/releases, GC и критическое переключение активных файлов/контейнеров проходят через общий artifact gate. Поэтому несколько активных copy jobs могут одновременно получать Git, но физическое копирование остаётся последовательным. Такое ограничение сохраняет согласованность квот и ссылок на артефакты.

Перед освобождением gate сборка уже имеет полный staging context, allocation receipt и durable `docker_build_reservation` со своим operation ID, release ID и уникальными тегами. Staging учитывается по фактическим bytes/inode. GC сохраняет allocation незавершённой операции; выбранные candidates, релизы и recovery points удерживаются по графу ссылок. Новый тег сборки не принадлежит retired release; дополнительная проверка запрещает удаление тегов активной reservation.

Docker preflight учитывает фактическое использование daemon **плюс** `build_reserve_bytes` других running/interrupted/unresolved сборок. Собственная reservation повторно не списывается при проверке результата. Суммирование проверяет overflow. После подтверждённого terminal result reservation перестаёт занимать логический бюджет; неопределённый исход сохраняет резерв. Пропавший owner record вызывает отказ учёта.

Это оценка и предварительный отказ, а не kernel reservation: размер слоёв и кеша BuildKit заранее точно неизвестен, внешние пользователи Docker могут менять свободное место. Панель повторно проверяет давление после сборки и перед переключением; она не запускает общий Docker prune и не удаляет защищённые артефакты ради следующего задания.

## Проверка реализации

`internal/executor/scheduler_test.go` выполняет настоящий async runner с управляемыми долгими участками: проверяет Rollback первым, одновременную работу трёх групп, независимые limits, повышение build slots до двух, сохранение resource conflicts и `queued` при занятом gate. `build_reservations_test.go` проверяет отказ превышающей бюджет второй сборки, сохранение reservation после interrupt и освобождение после подтверждённого terminal result. Эти тесты не заменяют нагрузочный прогон Docker на целевом Linux-хосте.
