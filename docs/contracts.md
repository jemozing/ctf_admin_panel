# Контракты доменной модели

Версия формата: `schema_version: 1`. Исполняемые контракты находятся в `internal/domain` и не зависят от HTTP, Docker SDK, SQLite и frontend. Этот документ фиксирует решения этапа 0; наличие контракта ещё не означает реализацию хранения, файлового копирования или переключения контейнеров.

## Идентичность и канонизация

`ID` — стабильный идентификатор длиной 1–64 символа из `[a-z0-9_-]`, начинающийся буквой или цифрой. Идентификаторы сервисов, релизов, снимков, операций и версий секретов не выводятся из имени каталога или container ID. Docker container ID хранится полностью: 64 шестнадцатеричных символа. `Digest` имеет вид `sha256:<64 lowercase hex>`.

Пути описываются каноническими POSIX-строками независимо от ОС разработчика. Абсолютные пути не могут быть `/`; относительные пути не могут быть пустыми, `.`, выходить через `..`, содержать обратный слеш, управляющие символы или невалидный UTF-8. Валидатор домена проверяет только строку. Это не защита от конкурентной замены symlink: executor обязан использовать безопасные операции относительно открытых дескрипторов и повторную проверку идентичности roots/mounts. Доступ к новому корню через веб-запрос не разрешается.

Канонический manifest — JSON без пробелов в фиксированном порядке полей структуры с entries, отсортированными по относительному пути. Digest вычисляется над этими байтами, включая версию схемы. Для Release сортируются множества образов, secret refs и data refs, время нормализуется в UTC. Порядок `compose_files` сохраняется: он влияет на смысл объединённой конфигурации. Не следует хешировать JSON сторонним универсальным сериализатором и ожидать совпадения: источником канонических байтов служат методы Go-контрактов.

## Service

`Service` — доверенная регистрация executor. Она содержит:

| Поля | Назначение |
|---|---|
| `id`, `name`, `description` | Идентичность и отображение |
| `project_directory` | Существующий активный проект |
| `source_directory` | Отдельное редактируемое дерево исходников |
| `compose_project`, `compose_files`, `profiles` | Точное имя проекта, порядок project-relative файлов и выбранные profiles |
| `managed_paths` | Непересекающиеся области кода/конфигурации и буквальные исключения |
| `data_paths` | Компонент, фактический источник хранилища, container target, значимость и допустимость потери |
| `targets` | Явные Compose components обычного обновления |
| `containers` | Подтверждённое соответствие component → полный container ID, image ID и роль |
| `policy_revision`, `file_map_revision` | Положительные монотонные ревизии |
| `secret_versions` | Ссылки на точные версии у executor без содержимого секретов |

В начальном профиле каждому Compose component соответствует один контейнер. Новая регистрация принимается после подтверждения Admin в панели неизменяемой заявки по digest и повторной проверки executor; CLI для этого не требуется. Корни и профиль привилегий задаются локально при установке. Наблюдаемый новый container ID после Deploy не является автоматическим расширением списка допустимых components.

`ManagedPath.Path` обозначает одинаковый относительный путь в active и source. `kind` — `code` или `configuration`; `exclusions` задаются относительно этой области и не являются glob. Вложенные managed roots запрещены, чтобы удаление кандидата не могло неоднозначно затронуть данные.

Для `bind` сохраняется абсолютный host source; для `named_volume` — фактическое имя существующего Docker volume, включая Compose prefix. Исходный volume key из YAML не заменяет идентичность реального хранилища. В начальном профиле любые `anonymous_volume`, а также значимые `writable_layer` и `tmpfs` блокируют пересоздание. Для явно временного writable layer/tmpfs администратор подтверждает допустимость потери; это не обещание сохранности. Известный, но неклассифицированный mount блокирует пересоздание.

Source workspace не пересекается с active project и bind-хранилищами; управляемые active paths не пересекаются с data binds. Две независимые регистрации одного Compose project или пересекающихся managed trees отклоняются. Явно общие постоянные хранилища регистрируются как зависимость и блокируются совместно только для затрагивающих их действий.

## Snapshot и Manifest

Snapshot имеет назначение `baseline`, `manual`, `candidate_source` или `recovery` и состояние `creating`, `complete`, `invalid` или `deleting`. `complete` требует совпадения manifest digest. Уровень согласованности явный: `coordinated_copy` означает согласованную работу команды без параллельных правок, `quiesced_copy` — дополнительно подтверждённое отсутствие записи во время копирования. Ни один уровень не объявляет копию согласованным бэкапом работающей БД.

`ManifestEntry` содержит путь, тип, размер, SHA-256, mode, UID/GID и при необходимости symlink target. Поддерживаются обычные файлы, каталоги и внутренние относительные symlinks. Ссылки сохраняются, не обходятся; manifest не содержит descendants через symlink или обычный файл. Device/FIFO/socket, setuid/setgid, sticky и file capabilities не принимаются в начальном профиле. Hardlinks в staging к active запрещены. Дополнительные обязательные атрибуты требуют отдельного расширения профиля.

`Manifest` не раскрывает изменяемые внутренние срезы; вход конструктора и возвращаемые entries копируются. Изменение UID, GID, mode, размера, контента или target меняет digest. Проверка digest подтверждает описание; фактические файлы всё равно нужно прочитать и сверить с manifest.

Baseline, pinned snapshots, снимки релизов и recovery незавершённой операции защищены от обычной ротации. Успешный snapshot не получает признака исправности приложения.

## Release и наблюдения

`NewRelease(ReleaseSpec)` создаёт неизменяемые канонические байты. `Spec()` и `CanonicalJSON()` возвращают копии. Изменение исходного source workspace, `.env`, срезов вызывающего кода или дополнительных результатов healthcheck не меняет Release.

Git-кандидат и релиз содержат необязательный `git_source`: URL, ref, точный commit, подкаталог и source revision. Для `source: git` provenance обязательна. Она не содержит credential и сохраняется неизменно вместе с кандидатом; `loadSnapshot` требует полного совпадения provenance в SQLite и snapshot artifact. Старые локальные снимки/релизы без этого поля сохраняют прежние канонические байты схемы 1.

Release содержит source snapshot, tree digest, digest сохранённой нормализованной конфигурации, ревизии, точные image ID, удерживающие теги, registry digests при наличии, ссылки на неизменяемые secret versions и декларации совместимости с данными. Удерживающий тег имеет вид `ctf-manager/<service_id>:<release_id>-<component>` и не заменяет проверку image ID. Поля с раскрытым environment/секретами в этот публичный контракт не входят. Артефакт конфигурации находится в защищённом хранилище executor и не выгружается в web без редактирования чувствительных значений.

События запуска и проверки хранятся отдельно как append-only `ReleaseEvent`. Статусы `prepared`, `active`, `locally_verified`, `failed`, `retired` вычисляются по событиям. `locally_verified` требует `local_functional`; ручное подтверждение отображается отдельным health signal и не маскируется под автоматическую проверку.

`ServiceStatus` разделяет desired release, current release, последний локально проверенный release и фактически наблюдаемые версии каждого component. При частичном переключении общий `current_release_id` не объявляется однозначным до сверки; per-component observations сохраняются. Неуспешная проверка нового релиза не возвращает поле active к старой версии.

Health signals независимы: состояние контейнера, Docker healthcheck, readiness, local functional, manual и external checker. Отсутствие проверки — `not_configured`, недоступность — `unknown`, истечение `valid_until` — `stale`. Ни running-контейнер, ни отсутствие checker не считаются успешной функциональной проверкой.

Rollback availability вычисляется заново перед остановкой работающего экземпляра: manifest, образы, конфигурация, секреты, действующая политика, совместимость данных и разрешённый drift. Старый успешный event не заменяет эти проверки. Rollback не вызывает build/pull.

## Operation

Спецификация операции содержит вид действия, service/release, инициатора, ключ идемпотентности, ожидаемую policy revision и active tree digest, timeout и список locks. Обязателен lock `service:<service_id>`. Список locks сортируется до захвата; дополнительные locks на Compose project, пути, контейнеры и общие данные вычисляет executor из доверенной политики.

| Переход | Условие |
|---|---|
| `queued → running` | Ресурсы получены и проверены |
| `running → succeeded` | Фактическое состояние известно, результат зафиксирован |
| `queued/running/interrupted → failed` | Фактическое состояние известно, результат и причина ошибки зафиксированы |
| `queued/running/interrupted → cancelled` | Известно состояние, результат сохранён; после активной мутации подтверждён возврат |
| `running → interrupted` | Обнаружена потеря процесса/ответа и нужна сверка |
| `interrupted → running` | Сверка установила фактическое состояние, предусмотрено продолжение |
| `running/interrupted → requires_recovery` | Нельзя подтвердить безопасный результат, сохранена причина |
| `requires_recovery → interrupted` | Явно начата предусмотренная сверка/восстановление |

`requires_recovery` удерживает конфликтующие ресурсы и не считается окончательным успешным завершением. `succeeded`, `failed`, `cancelled` не возобновляются. Стадия (`copying`, `building`, `switching` и т. п.) хранится отдельно от состояния.

`BeginMutation` фиксирует границу изменения active state. Deploy/Rollback/Recover требуют recovery point до этой границы. Чистая модель не обеспечивает долговечность сама: движок обязан записать намерение в SQLite с подходящей синхронизацией **до** побочного действия, а фактический результат — после. Таймаут клиента не является отменой операции. Повтор запроса с тем же инициатором, ключом и параметрами возвращает ту же операцию; с другими параметрами отклоняется.

## Проверки контрактов

`go test -race ./internal/domain` проверяет разделение source/data, запрет значимого неподдерживаемого storage, конфликтующие регистрации, обход путей/symlink, неизменяемость manifest/release, привязку атрибутов к digest, versioned secrets, запрет ложного success/cancel и слепого продолжения после сбоя, stale health и удержание recovery. Проверки на реальных Docker и файловой системе относятся к последующим этапам и не заменяются этими unit tests.

## Код внутри disposable bind

`DataPath.allow_code_updates` — необязательный boolean, по умолчанию false. Он разрешает пересечение управляемых путей с конкретным writable bind внутри ProjectDirectory только вместе с `significant=false` и `loss_accepted=true`. Компонент должен входить в Targets; свежая policy проверяет также остальные runtime consumers кода. Persistent binds без этого opt-in по-прежнему не пересекаются с managed paths. Флаг не меняет host/source/target identity, правила workspace, symlink/parent guards или конфликты независимых сервисов. Disposable code binds не являются DataReference постоянных хранилищ; release evidence помечает их `code_bind_loss_accepted`, с отдельной отметкой при одновременном наличии сохраняемых данных.
