# Релизный pipeline текущей реализации

После подтверждения регистрации в панели автоматически ставится **Snapshot**: executor фиксирует baseline управляемых файлов, импортированный релиз и удерживающие теги точных локальных image IDs всех компонентов. Игровые данные из `data_paths` не копируются. Для веб-регистрации приватный workspace публикуется из baseline целиком с receipt/маркером инициализации; после сбоя его можно завершить повторным Snapshot через панель. Существующие авторские правки не перезаписываются. Дополнительный локальный `propose → approve` требует отдельного первого Snapshot, как прежде.

Для локального источника оператор меняет файлы отдельного `source_directory`, затем **Prepare** фиксирует неизменяемый кандидат. Для настроенного HTTPS Git-источника **Fetch source** создаёт кандидат напрямую из точного commit, не перезаписывая локальный workspace. **Build** материализует выбранный кандидат в приватном временном каталоге, собирает только явно зарегистрированные targets и создаёт ReleaseSpec со снимком, image IDs, версиями секретов и утверждённой конфигурацией; Git provenance переносится в релиз. Правки workspace или перемещение ветки после подготовки не меняют этот кандидат. Compose-файлы из кандидата не могут менять утверждённую конфигурацию: изменение зафиксированного Compose-входа требует отдельного одобрения новой политики, редактора такой политики текущий мастер не предоставляет. Build не пишет в активные bind mounts.

Каждое действие проходит `Preview → plan_digest → Submit`. План связывает сервис, ревизию, фактический digest активных файлов, кандидат/релиз, список компонентов и изменения файлов. Изменившийся или непроверенный план отклоняется. Повтор одного actor/idempotency key с тем же запросом возвращает прежнюю операцию даже после изменения состояния сервиса; другой запрос с тем же ключом отклоняется.

**Deploy/Rollback** перед остановкой проверяет сохранённые файлы, точные локальные образы, версии секретов, утверждённые настройки runtime и совпадение активных файлов с текущим релизом. Затем сохраняет recovery point и намерение мутации в SQLite, останавливает только targets, применяет управляемые файлы и вызывает Compose `up --no-build --pull never --no-deps --force-recreate` для этих компонентов. БД/зависимости не пересоздаются. `down`, удаление volumes и восстановление БД не входят в pipeline. Совместимость кода с текущими постоянными данными подтверждается отдельно.

Новый фактический релиз записывается **до** проверок. Running, Docker healthcheck, readiness, local functional и внешний checker — независимые сигналы. Ошибка после начала мутации оставляет `requires_recovery` и блокировки; ложный успешный результат не записывается.

## Проверки приложения

Локальный администратор может добавить в политику `checks` (не более 16). Это ограниченные HTTP GET из сетевого пространства executor, без redirect, shell и передачи произвольной команды через Web:

```json
{
  "checks": [
    {"id":"ready","source":"readiness","url":"http://reachable-service:8080/health","expected_status":200,"timeout_seconds":3},
    {"id":"functional","source":"local_functional","url":"http://reachable-service:8080/status","expected_status":200,"body_contains":"expected response marker","timeout_seconds":3}
  ]
}
```

Адрес должен быть достижим именно из executor-контейнера; `127.0.0.1` внутри него относится к executor. Название и URL проверки утверждаются вместе с политикой. Тело ответа ограничено 64 KiB, время одной проверки — 10 секунд. Ответы и их содержимое не записываются в журнал. Проверки выполняются после переключения, запуска/рестарта и восстановления; их результат становится `stale` через 30 секунд. Периодический функциональный мониторинг и сценарии с записью/чтением/удалением тестового флага остаются отдельным расширением. Наш интеграционный стенд проверяет сохранность флага внешним тестом.

## Прерывание и восстановление

При рестарте `running` становится `interrupted`; блокировки и recovery point сохраняются. Никакие файловые или Docker-шаги не повторяются автоматически. Собственный stale Unix socket можно восстановить только под эксклюзивным flock после подтверждённого ECONNREFUSED; живой или чужой socket не удаляется.

Оператор выбирает прерванную операцию и проверяет новый план **Recover**. Executor сохраняет отдельное намерение с actor и ключом, продолжая использовать исходную операцию и её блокировки. Сохранённые локальные файлы/образы возвращают предыдущий релиз без build/pull; постоянные данные не откатываются. После подтверждённого возврата исходная операция становится `failed` с `returned_to_previous=true`. Новый сбой снова требует свежего плана восстановления. Вмешательство в незатронутые зависимости или неподдерживаемый runtime блокирует автоматический возврат и требует локальной сверки администратора.

## CLI при недоступном dashboard

Все действия идут в тот же Unix executor. Файл запроса содержит фиксированные поля:

```json
{"service_id":"example","action":"rollback","release_id":"rel-REVIEWED_ID","idempotency_key":"unique-request-key"}
```

```sh
bin/ctf-manager --config var/executor.dev.json preview --request request.json
bin/ctf-manager --config var/executor.dev.json submit --request request.json \
  --plan sha256:REVIEWED_PREVIEW_DIGEST --confirm-data
bin/ctf-manager --config var/executor.dev.json operation --operation op-RETURNED_ID
bin/ctf-manager --config var/executor.dev.json events --operation op-RETURNED_ID
```

Для восстановления в запросе используется `action: "recover"` и `recovery_operation_id` исходной операции. Остановка CLI или браузера не отменяет задачу.

## Границы приёмки

Интеграционные стенды с named volumes и production bind mounts покрывают baseline, Prepare/Build без изменения active, Deploy, Rollback, одинаковый ключ и явный Recover. Параметризованная серия прошла шесть SIGKILL границ, потерю ответов Submit/Stop, API503 и исчезновение компонента. Проверены ротация, квоты, реальный ENOSPC, нехватка inode и backup/restore в новый каталог. Пятиминутная нагрузка с host/container metrics прошла на доступной OrbStack VM. Контейнерные проверки выполнены на arm64 и с amd64-бинарником через эмуляцию. Полная матрица аварий A14, нагрузочная приёмка на опорной VM, native Linux amd64, недоступность registry самому daemon, UI отмены и общая приёмка целевого vulnbox остаются открытыми. Подробные результаты приведены в [матрице приёмки](progress.md), [описании хранения](storage.md), [метриках](metrics.md) и [инструкции backup/restore](backup.md).
