# Резервное копирование панели

`ctf-manager backup` и `ctf-manager restore` — локальные административные команды. Они не обращаются к Docker, не останавливают игровые контейнеры, не копируют и не откатывают игровые БД/volumes. Команды доступны до загрузки глобального `--config`: пути задаются явными флагами.

## Два режима

| Режим | Что сохраняется | Применение после восстановления |
|---|---|---|
| По умолчанию, `metadata` | Новые БД из разрешённых полей: каталог сервисов и карты файлов, manifests релизов/снимков, ссылки на образы и секреты, состояния операций и блокировки; пользователи, Argon2id-хеши и роли dashboard; типизированный bootstrap | Каталог для проверки и повторной регистрации. Каждый сервис заблокирован для операций до новой локальной регистрации и утверждения более высокой ревизии |
| С `--passphrase-file` или `--passphrase-stdin`, `protected_full` | Согласованные полные БД executor/dashboard, bootstrap, защищённые версии секретов, содержимое снимков, материализованные runtime inputs | Рабочее состояние панели при наличии внешних проектов, образов и игровых данных по исходным путям; незавершённые операции требуют явной сверки |

Обычный экспорт исключает раскрытый Compose, `command`/`entrypoint`, environment, URL проверок, исходные файлы, vault, inputs заданий, произвольные диагностические сообщения, журналы операций и аудит с произвольным текстом. БД **создаются заново по белому списку**: удаление чувствительных строк из копии БД оставило бы их в свободных страницах SQLite. Текстовые названия заменяются ID, описания и детали проверок исключаются. Имена файлов, пути, пользователи и другие структурные метаданные остаются чувствительными административными данными; файл экспорта имеет mode `0600`.

Protected full шифрует весь архив с помощью AES-256-GCM. Ключ выводится Argon2id (`m=65536 KiB`, `t=3`, `p=1`) с новой 128-битной солью. Независимо аутентифицируются последовательные блоки до 1 MiB, заголовок, номера блоков и обязательная финальная запись. Неверная фраза, перестановка, повреждение, усечение и добавление блоков приводят к отказу. Фраза должна содержать 16–4096 байт; передача её значением аргумента или environment не поддерживается. Фраза не включается в backup. Потеря фразы делает protected full невосстановимым.

Оба режима исключают Docker images, активные проекты, source workspaces, игровые bind mounts и volumes. JSON-отчёт и `manifest.json` перечисляют внешние зависимости и отсутствующие в экспорте артефакты. `docker_image_not_included` означает, что образ нужно сохранить отдельной процедурой или оставить в исходном daemon; команда не проверяет его наличие в Docker.

## Согласованное создание

После захвата maintenance locks и открытия проверенной БД экспорт записывает immutable `maintenance_audit`: UTC, локальный UID, режим, request ID, digest назначения и результаты `started`/`succeeded`/`failed`. Произвольные ошибки, пути и секретные значения в это событие не включаются. `audit_request_id` возвращается в отчёте. Конечный результат хранится в исходной БД после публикации архива; внутри самого архива доступна предшествующая запись начала. Отказ записи аудита не выдаётся за успешное обслуживание.

Перед backup остановите **оба процесса панели**, включая дополнительные административные CLI, открывающие state. Игровые проекты останавливать не требуется:

```bash
docker compose --env-file /srv/ctf-manager/config/compose.env stop dashboard executor
sudo install -d -m 0700 /srv/ctf-backups
```

Приложения удерживают shared flock своего state-каталога весь срок жизни. Backup берёт оба exclusive flock в фиксированном порядке и немедленно отказывает, если один процесс ещё работает. Копирование открытого `.db` не применяется: обе БД сначала сохраняются через SQLite `VACUUM INTO`, включая подтверждённые WAL-страницы. Затем при необходимости формируются новые очищенные БД. Приватный временный каталог удаляется после завершения; окончательный файл публикуется только после записи manifest и `fsync` и никогда не заменяет существующий backup.

Обычный экспорт:

```bash
sudo ./bin/ctf-manager backup \
  --executor-state /srv/ctf-manager/executor \
  --dashboard-state /srv/ctf-manager/dashboard \
  --configuration /srv/ctf-manager/config/executor.json \
  --output /srv/ctf-backups/panel-metadata.tar
```

Protected full, с заранее подготовленным приватным файлом фразы:

```bash
sudo ./bin/ctf-manager backup \
  --executor-state /srv/ctf-manager/executor \
  --dashboard-state /srv/ctf-manager/dashboard \
  --configuration /srv/ctf-manager/config/executor.json \
  --output /srv/ctf-backups/panel-full.ctfmbak \
  --passphrase-file /root/ctfm-backup.pass

docker compose --env-file /srv/ctf-manager/config/compose.env up -d
```

Файл фразы должен быть regular file с правами `0600` или строже; symlink отклоняется. Удаляется один конечный LF. По умолчанию предел содержимого артефактов — 64 GiB; `--max-bytes` задаёт меньший или больший явный предел. Дополнительно ограничены число файлов (200000) и размер manifest (16 MiB). Место требуется для согласованных копий SQLite и итогового архива. Сам архив размещается **вне обоих state-каталогов**.

Если на Linux нет native binary, можно запустить команду из собранного executor image отдельным контейнером. Ему нужны только state и каталог экспорта; Docker socket и игровые корни не монтируются:

```bash
docker run --rm --network none --read-only \
  --cap-drop ALL --cap-add CHOWN --cap-add DAC_OVERRIDE --cap-add FOWNER \
  --mount type=bind,src=/srv/ctf-manager,dst=/srv/ctf-manager \
  --mount type=bind,src=/srv/ctf-backups,dst=/backups \
  --mount type=bind,src=/root/ctfm-backup.pass,dst=/run/backup.pass,readonly \
  ctf-manager-executor:local backup \
  --executor-state /srv/ctf-manager/executor \
  --dashboard-state /srv/ctf-manager/dashboard \
  --configuration /srv/ctf-manager/config/executor.json \
  --output /backups/panel-full.ctfmbak --passphrase-file /run/backup.pass
```

State mount остаётся writable для SQLite и maintenance locks. Это отдельный административный запуск после остановки Compose, без сети и Docker API. Не добавляйте dashboard state к постоянным mounts executor.

## Восстановление

Восстановление допускается только в **новый, ещё не существующий** каталог:

```bash
sudo ./bin/ctf-manager restore \
  --input /srv/ctf-backups/panel-full.ctfmbak \
  --destination /srv/ctf-manager-restored \
  --passphrase-file /root/ctfm-backup.pass
```

Для metadata флаг фразы не задаётся. Результат:

```text
/srv/ctf-manager-restored/
  executor/executor.db
  executor/snapshots/     # только protected full
  executor/secrets/       # только protected full
  dashboard/dashboard.sqlite
  config/executor.json
  restore-report.json
```

Команда проверяет белый список путей, отсутствие traversal, symlinks/hardlinks/devices, дубликатов и неподдерживаемых tar-расширений, размеры, SHA-256 и права каждого файла, целостность обеих SQLite БД и внешние ключи executor. Для protected full дополнительно проверяются manifests и содержимое восстановленных снимков; пустые управляемые каталоги восстанавливаются из manifests. Состояние подготавливается в приватном staging и публикуется атомарным rename с запретом замены существующего каталога. Ошибки проверки не публикуют частичное состояние. Исходный backup и текущая панель не заменяются.

Перед первым запуском:

1. Проверьте `restore-report.json`: образы и игровые данные в backup не входят; отсутствующие/отозванные версии секретов и недоступные артефакты указаны отдельно.
2. Убедитесь, что внешние проекты, source workspaces, named volumes, Docker images и фактические данные существуют. Панель не воссоздаёт их автоматически.
3. Сохраните прежний state отдельно и остановите старые процессы. Перенесите восстановленные каталоги по исходным абсолютным host-путям либо подготовьте проверенные новые bootstrap/Compose mounts. `original_state_directory` в отчёте и `config/executor.json` сохраняют исходный путь; команда не переписывает автоматически игровые пути или frozen Compose. Для нового корня особенно проверьте runtime inputs и источники bind mounts.
4. Сохраните разделение владельцев: executor state принадлежит executor UID, dashboard state — web UID, оба `0700`. Root-восстановление сохраняет исходные UID/GID; без root допускается восстановление только собственного UID.
5. Запустите dashboard/executor и войдите заново. Прежние сессии исключаются из копии и удаляются при восстановлении и запуске web. `queued` из backup переведены в `cancelled`; `running` — в `interrupted`, блокировки сохраняются. Непотреблённые `recovery_request` из backup помечаются потреблёнными: прежнее подтверждение Recover также не воспроизводится. Для незавершённого переключения используйте новый явный Recover после предпросмотра.
6. После metadata restore локально выполните новую регистрацию и утверждение каждой политики. До более высокой утверждённой ревизии Submit и автоматическая очистка артефактов этого сервиса заблокированы. Старые manifests сохраняются для проверки; их контент и секреты не появляются от повторной регистрации.

Если metadata export содержит незавершённые операции, их блокировки также сохраняются. Повторная регистрация сама по себе не снимает эти блокировки и не делает прежний Recover исполнимым без отсутствующих артефактов старой ревизии. Такая копия служит каталогом для локальной сверки; для полноценного восстановления незавершённого переключения используйте protected full и исходные внешние зависимости. Автоматического «забыть блокировку и продолжить» нет.

Резервирование каталога панели не обеспечивает согласованную копию игровых БД и не заменяет отдельное резервирование данных соревнования. Копия на том же диске не защищает от его потери. Вынос protected full и отдельное безопасное хранение фразы выполняются локальным администратором.

## Проверки реализации

`go test ./internal/backup ./internal/maintenance ./internal/store` проверяет:

- согласованный SQLite snapshot с подтверждёнными изменениями в WAL;
- отсутствие контрольного секретного значения во всём обычном tar, включая SQLite pages, при наличии значения в source/vault/Compose/операционных inputs/журналах/описаниях/аудите;
- protected full roundtrip БД, секретов и снимка с пустым каталогом;
- отзыв сессий, отмену очереди и сохранение блокировок прерванной операции;
- отказ при живом shared lock, превышении лимита, неверной фразе, повреждении или усечении ciphertext;
- отказ при traversal, ссылках, повреждении хеша и существующем destination.
