# Логи и диагностика операций

Логи контейнеров и журналы операций имеют разные источники. Container logs зависят от logging driver и существования контейнера. Критический журнал executor хранит принятые запросы, этапы, намерения переключения, наблюдаемые результаты и переходы состояний независимо от контейнерных логов.

## Структурированные логи сервисов

Общий stdout/stderr поток сохраняет timestamp, container/component identity и источник. Перед фильтрацией и выдачей выполняются `redact → sanitize → byte cap`: известные приватные значения скрываются до усечения, управляющие символы заменяются безопасным текстом, каждая строка ограничена 16 KiB по корректной границе UTF-8. В ответе не более 500 records и 96 KiB текста. Неполная исходная строка отбрасывается, чтобы не публиковать фрагмент секрета; источники и ответ явно сообщают об усечении/ошибке. Текст не исполняется как HTML.

Search, RE2 include/exclude и time selectors ограничены контрактом. Медленный WebSocket reader имеет deadline записи и не создаёт неограниченную очередь; отдельный viewer продолжает получать кадры. Проверки длинных строк, control expansion, частичных/поддельных frames, фильтров и backpressure приведены в [security report](../tests/integration/reports/README.md#report-security-acceptance-2026-10-20-json).

## Build и Compose

Вывод stdout/stderr Docker Compose Build и переключения сохраняется в отдельной таблице `operation_diagnostics` БД executor, включая вывод неуспешной сборки. Каждая часть содержит operation ID через родительскую операцию, последовательность, UTC, этап и текст. Он доступен только пользователям с разрешением `sensitive_access`; Viewer без этого разрешения не получает диагностику через API.

Перед записью заменяются известные значения из environment и file-backed inputs замороженной конфигурации. Замена распознаёт значение, разделённое между несколькими записями stdout/stderr. Управляющие символы удаляются, CR преобразуется в перевод строки, неверный UTF-8 заменяется. В интерфейсе содержимое выводится текстом. Если набор известных значений превышает ограничение обработки, вместо необработанного вывода сохраняется явное сообщение о сокрытии диагностики.

Редактирование известных значений не гарантирует распознавания нового секрета, напечатанного Dockerfile, его кодированной формы или игровых данных. Поэтому доступ остаётся чувствительным; файлы diagnostics не публикуются как общедоступные артефакты. Build evidence хранит отдельно ограниченный digest исходного вывода и не содержит его открытого текста.

## Ограничения и загрузка

Хранится хвост до **20 MiB на операцию** и до **200 MiB суммарно**. При превышении удаляются старые части диагностического вывода и увеличивается долговечный `dropped_bytes`. Эти лимиты относятся к содержимому; SQLite может сохранять свободные страницы и WAL, поэтому они не являются физической FS-квотой. Общая квота executor state проверяется отдельно.

Очистка диагностики не удаляет audit/state events, намерения изменения, результаты операций или блокировки. Перезапуск панели сохраняет доступный вывод и счётчики потерь. Ошибка записи диагностического журнала возвращается вызывающей операции, а не превращается в успешный результат Compose.

API выдаёт страницы по `after` sequence cursor: до 32 частей по 32 KiB, не более 1 MiB текста до JSON escaping. В ответе находятся `chunks`, сохранённые `bytes`, `returned_bytes`, `next_sequence`, `has_more`, `dropped_bytes` и `truncated`. Пропущенная из-за ротации история отмечается явно. Клиент догружает страницы с последнего sequence; порядок stdout/stderr не является точным глобальным порядком событий разных процессов.

Тесты проверяют сохранение stderr неуспешного Compose, редактирование через границы записей, отказ при ошибке persistence, ограничения и курсоры, перезапуск БД и сохранность критического журнала при ротации диагностики.

## Ожидание ресурсов

Для queued операций API добавляет read-only `queue_wait`: причину ожидания, lane и его лимит, список блокирующих ресурсов, operation ID и инициатора владельца. `resource_locked` вычисляется по фактической таблице locks с той же проверкой пересечения путей, что применяется при захвате. `lane_limit` показывает наблюдаемые running задания соответствующего типа; `scheduler` обозначает ожидание диспетчеризации без установленного владельца ресурса. Это текущий срез, который может измениться к следующему запросу. Running и terminal операции не получают такой отметки.

Наблюдение не захватывает блокировки, не продлевает таймаут и не создаёт записи критического журнала. Производные поля нельзя сохранить обратно в operation payload или использовать вместо повторной проверки при запуске задания.
