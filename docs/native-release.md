# Сборка нативных пакетов

Нативная поставка — два Linux-архива для `amd64` и `arm64`. В каждом находятся пять статических Go-бинарников, встроенный в `ctf-manager` frontend, установщик, две systemd-службы, пример конфигурации, документация, лицензия и контрольные суммы. На целевом сервере не нужны Go, Node.js или исходники.

## GitHub Actions

После добавления workflow в основную ветку откройте **Actions → Native release → Run workflow** и выберите ветку:

- Пустое поле версии — проверочная сборка `dev-<12 символов commit SHA>`.
- Явная версия, например `v0.1.0` — имя пакета и версия бинарника. Ручной запуск собирает файлы, но не публикует GitHub Release.

Артефакт **native-linux-packages** содержит:

```text
ctf-manager_VERSION_linux_amd64.tar.gz
ctf-manager_VERSION_linux_arm64.tar.gz
SHA256SUMS
```

Артефакты Actions предназначены для загрузки после сборки и имеют ограниченный срок хранения. В каждом tar.gz есть собственный `SHA256SUMS` и `release.json` с архитектурой, версией, commit и сведениями о бинарниках. [Установка скачанного архива](native-install.md).

Pull Request с изменениями поставки также запускает проверочную сборку. Она не создаёт релиз и не устанавливает пакет на пользовательском сервере.

## Опубликовать версию

Публикация отделена от ручной проверочной сборки. После прохождения проверок и слияния изменений создайте новый semver-тег вида `v0.1.0` на нужном commit и отправьте его в репозиторий:

```sh
git switch main
git pull --ff-only
git tag v0.1.0
git push origin v0.1.0
```

Это намеренное действие выпуска: tag-workflow собирает архивы и публикует их вместе с контрольными суммами в GitHub Releases. Не используйте уже существующую версию для другого содержимого. Доступ записи `contents: write` получает только job публикации; сборка выполняется с правами чтения.

## Собрать локально

Нужны Go 1.26+, Node.js 22.12+, npm и Python 3.10+. Для первой загрузки закреплённых зависимостей требуется сеть:

```sh
make native-release VERSION=v0.1.0
```

По умолчанию выполняются сборка frontend и cross-build обеих архитектур. Выходные файлы сохраняются в `dist/`. Тот же процесс доступен напрямую через `python3 scripts/build-native-release.py --version v0.1.0`. Для одной архитектуры:

```sh
python3 scripts/build-native-release.py \
  --version v0.1.0 --arch amd64 --output-dir dist
```

Если frontend уже собран из текущих исходников, можно избежать повторного шага:

```sh
make frontend
python3 scripts/build-native-release.py \
  --version v0.1.0 --arch amd64 --arch arm64 --skip-frontend
```

`--skip-frontend` требует существующий `web/dist/index.html` и доверяет вызывающему в том, что frontend актуален. Go собирается с `CGO_ENABLED=0`, `GOOS=linux`, `-trimpath` и версией пакета. Состав архива ограничен явным списком: локальные БД, конфигурации, игровые файлы, кэши, `node_modules` и `.git` не входят в поставку.

Перед проверкой пакета используйте новую версию или отдельный output-каталог. Установка на Linux и проверка systemd описаны отдельно; успешный cross-build на macOS сам по себе не подтверждает работу служб на целевом хосте.
