# CTF Service Manager — техническое задание

Версия документа: 2.14

Дата: 2 ноября 2026 года
Назначение: разработка панели управления сервисами команды на Attack/Defense CTF.

Обязательный профиль соревнований — `competition-4g`: 4 vCPU, 4 GiB RAM и виртуальный диск 40 GiB. Прежний профиль `legacy-8g` сохраняется отдельно для сопоставления измерений (§17.3). Эта версия уточняет требования и условия испытаний; она не объявляет приёмку пройденной. Фактические результаты и оставшиеся проверки ведутся в [матрице приёмки](progress.md).

## 1. Назначение и границы продукта

CTF Service Manager устанавливается на Linux-сервер команды — vulnbox — и помогает участникам регистрировать существующие Docker Compose-проекты, готовить исправления, развёртывать их и возвращаться к предыдущему рабочему релизу.

Основной сценарий:

1. Участник готовит исправления сервиса.
2. Панель создаёт изолированный кандидат и показывает изменения.
3. Кандидат проверяется и собирается без изменения работающего приложения.
4. Участник применяет подготовленный релиз.
5. Панель переключает нужные контейнеры, выполняет проверки и сохраняет результат.
6. При необходимости участник возвращает предыдущий релиз без пересборки и скачивания образов.

Единица управления — игровой сервис, который может состоять из приложения, БД, кеша и других контейнеров одного Compose-проекта.

Первая версия рассчитана на одну доверенную команду и один хост. Панель не является платформой организаторов, системой выдачи флагов, scoreboard или средством изоляции разных команд. Полная компрометация хоста выходит за пределы обеспечиваемой защиты.

Термин «должен» обозначает обязательное требование соответствующего выпуска. Возможности после MVP обозначены явно и не входят в критерии готовности MVP.

### 1.1. Приоритеты

В порядке убывания важности:

1. Сохранение игровых данных и существующей конфигурации сервисов.
2. Возврат подготовленного рабочего релиза без сборки и внешней сети.
3. Предсказуемое поведение при ошибках и аварийном завершении панели.
4. Быстрое применение исправлений и понятный результат операции.
5. Небольшое потребление ресурсов vulnbox.

Нулевой простой при обновлении не гарантируется. Для каждого поддерживаемого сценария измеряется длительность переключения и восстановления.

## 2. Состав MVP и последующих выпусков

### 2.1. Обязательный состав MVP

| Область | Возможности |
|---|---|
| Развёртывание | Linux + Docker Compose, два контейнера `dashboard` и `executor`, встроенный frontend и один Go-бинарник в двух режимах |
| Доступ | Локальные пользователи, серверные сессии, роли Admin/Defender/Viewer, аудит |
| Привилегии | Разные UID контейнеров, локальный Unix socket; Docker socket доступен только executor |
| Подключение | Регистрация существующего Compose-проекта через веб по пути внутри разрешённого корня; обнаружение контейнеров/хранилищ, просмотр и подтверждение заявки Admin в панели без CLI |
| Git-источник | GitHub/GitLab и другие Git-серверы по HTTPS Git URL, ветка/tag/точный commit, необязательный read-only токен; ручное получение неизменяемого кандидата без изменения работающего сервиса |
| Инвентаризация | Контейнеры, образы, порты, mounts, зависимости, исходная конфигурация запуска |
| Управление | Start, Stop, Restart для подтверждённых целей |
| Снимки | Baseline, ручные снимки управляемых файлов, проверка целостности, ротация |
| Релизы | Неизменяемые записи релизов, сохранение образов и конфигурации запуска |
| Подготовка | Копирование управляемых файлов в staging, diff, проверка конфигурации, отдельная сборка |
| Обновление | Ручной запуск подготовленного релиза с ограниченным набором затрагиваемых контейнеров |
| Откат | Ручной возврат сохранённого релиза без build/pull и без отката игровых данных |
| Проверки | Настраиваемые локальные проверки и раздельное отображение их результатов |
| Операции | Фоновые задания, блокировки, защита от повторных запросов, восстановление после сбоев |
| Диагностика | Live-логи, поиск и regex, журналы операций, базовые метрики хоста и контейнеров |
| Восстановление панели | Резервирование её БД и конфигурации, аварийный локальный CLI |

В MVP доступны два источника кандидата: отдельный зарегистрированный каталог подготовки исходников (`source workspace`) и Git URL. Локальный workspace создан из управляемых файлов сервиса, находится вне активного дерева и игровых mounts; участник может редактировать его привычным редактором. Действие «Получить из Git» разрешает ref в точный commit, получает исходники в изолированном каталоге и создаёт неизменяемый кандидат только из разрешённых управляемых путей. Далее используется общий Build → Deploy. Получение из Git не меняет локальный workspace, активные файлы, контейнеры и игровые данные; перемещение ветки не меняет уже подготовленный кандидат.

### 2.2. После MVP

| Выпуск | Возможности |

Отдельный этап 9, требования §18.8 |

Нумерация последующих выпусков обозначает порядок расширения, а не обязательство реализовать весь список. Каждый выпуск должен сохранять гарантии MVP.

### 2.3. Что не входит в MVP

- Управление несколькими хостами и удалённые агенты.
- Универсальный импорт произвольного `docker run`.
- Автоматическое изменение сетевой конфигурации Docker или firewall хоста.
- Бэкап и восстановление содержимого БД, volumes и других игровых данных.
- Полное восстановление vulnbox после потери диска.
- Автоматические миграции схемы БД и автоматический возврат схемы назад.
- Встроенный терминал, произвольные команды и редактор файлов в браузере.
- HTTP Proxy, журнал трафика и базовый WAF разрабатываются отдельным расширением (§18.8); они не входят в приёмку MVP A01–A39. Пассивные пакеты/PCAP реализуются независимым opt-in расширением (§18.7), с отдельной C-матрицей.
- Обязательные внешние БД, Redis, Prometheus и Grafana.

## 3. Архитектура и стек

| Компонент | Решение |
|---|---|
| Backend и CLI | Go |
| Frontend | React + TypeScript |
| UI | shadcn/ui |
| Раздача frontend | `embed.FS` из устанавливаемого бинарника |
| Метаданные | SQLite в режиме WAL на локальной файловой системе |
| Docker | Docker Engine API через Go SDK |
| Compose | Установленный Docker Compose CLI plugin |
| Потоки логов и операций | WebSocket с проверкой сессии и Origin |
| Метрики | Docker Stats API, Linux `/proc` и `/sys` |
| Файловые снимки | Полные копии управляемых файлов, manifest с хешами |
| Установка | Multi-stage Dockerfile, Compose, локальный root bootstrap и конфигурация |

Архитектура — модульный монолит с разделением привилегий между двумя контейнерами одного бинарника. React собирается на стадии сборки и встраивается в Go через `embed.FS`; отдельный Node.js-сервер в рабочей установке не запускается. Основной способ запуска — Docker Compose. Нативный бинарник остаётся альтернативой для разработки и диагностики.

```text
Участники команды
        │ HTTPS через приватную сеть / SSH-туннель
        ▼
dashboard: ctf-manager dashboard     UID/GID 10001:10001
  ├── HTTP API и Web UI
  ├── Авторизация и роли
  └── Пользовательские метаданные
        │ типизированный протокол, Unix socket
        ▼
executor: ctf-manager executor       UID/GID 0:10001
  ├── Проверка полномочий операции
  ├── Доверенная конфигурация сервисов
  ├── Журнал выполнения и блокировки
  ├── Staging, снимки, релизы
  ├── Получение кандидатов из Git    изолированный процесс UID/GID 65534
  └── Docker API / Compose CLI
        │
        ▼
Существующие игровые контейнеры
```

Executor имеет доступ к Docker socket и необходимые права на управляемые файлы. Web-процесс не имеет доступа к Docker socket, записи в доверенное хранилище executor или прямого изменения его политик.

Разделение на внутренние Go-пакеты не считается границей безопасности. Разделение UID, файловых разрешений и протокола между контейнерами обязательно для MVP. Общий GID используется только для доступа к Unix socket. Протокол дополнительно проверяет UID подключившегося процесса через Linux peer credentials; доступ к каталогу socket не заменяет эту проверку.

Отказ web или executor не должен останавливать игровые контейнеры. Обновление и остановка панели не должны выполнять `compose down` или иные действия с сервисами автоматически.

## 4. Развёртывание и эксплуатационные предпосылки

### 4.1. Поддерживаемая среда

- Linux-хост с локальной файловой системой и работающим Docker Engine; systemd внутри контейнеров не используется.
- Docker Compose plugin с возможностями, используемыми поддерживаемым профилем.
- Архитектура хоста, для которой опубликованы образы панели; первым обязательным целевым вариантом является linux/amd64. Linux/arm64 проверяется отдельно; Docker Desktop на macOS пригоден для разработки и не заменяет Linux-приёмку.
- Доступ к панели через loopback/SSH-туннель или приватный интерфейс с HTTPS.

Точные поддерживаемые версии дистрибутивов, Docker и Compose фиксируются в матрице совместимости релиза и проверяются в интеграционных тестах. Установщик должен проверять возможности среды, а не предполагать их наличие по имени дистрибутива.

Для завершающей приёмки MVP выбран отдельный Linux/amd64 стенд профиля `competition-4g` (§17.3). По [инвентаризации VM от 29 октября](../tests/integration/reports/README.md#report-native-vm-inventory-2026-10-29-json) это Ubuntu 26.04.1 LTS, 4 vCPU, 4 GiB online physical memory в адресном пространстве гостя и виртуальный диск 40 GiB. Linux и Docker видят `MemTotal = 3 563 139 072` байта (около 3,318 GiB); в частности, 512 MiB зарезервированы crashkernel. Swap отсутствует. Диск представлен как `VBOX HARDDISK` через виртуальный SATA-контроллер; тип физического накопителя хоста и NVMe не подтверждены. Эти сведения описывают доступный стенд, а не результат функциональных или нагрузочных испытаний.

### 4.2. Установка через Docker Compose

В поставке находятся `Dockerfile`, `compose.yaml` и локальный bootstrap `scripts/compose-bootstrap.py`. Dockerfile собирает frontend и Go-бинарник, затем создаёт два runtime-образа: `dashboard` без Docker CLI и `executor` с закреплёнными Docker CLI, Compose и Buildx. Docker daemon внутри панели не запускается; executor обращается к существующему daemon хоста.

Bootstrap запускается root на самом Linux Docker-хосте и должен:

1. Проверить канонические абсолютные пути, отсутствие symlink-компонентов служебных каталогов, владельцев, права и локальный Docker socket.
2. Создать отдельные каталоги dashboard, executor, IPC и bootstrap-конфигурации; не менять владельцев/содержимое существующих игровых проектов.
3. Зафиксировать явно разрешённые корни обнаружения и source workspaces; корень `/` не допускается.
4. Создать root-owned конфигурацию executor и Compose override только с разрешёнными bind mounts.
5. Предоставить локальную процедуру создания первого администратора.
6. Вывести команду `docker compose --env-file /srv/ctf-manager/config/compose.env up -d --build`.

Перед запуском выполняется `docker compose ... config --quiet`; после запуска — preflight Docker/Compose и проверка готовности IPC. Отсутствующие host-каталоги не создаются Docker автоматически: используются long bind mounts с `create_host_path: false`. Изменение разрешённых корней требует локального административного изменения конфигурации и пересоздания executor.

Создание первого администратора выполняется через локальный CLI в контейнере dashboard, без стандартного пароля и публичной регистрации. Пароль не передаётся аргументом командной строки или в Compose environment.

Установка не меняет настройки Docker daemon, не перезапускает Docker, не переназначает игровые порты и не меняет firewall. Игровые контейнеры остаются в своих Compose-проектах, без `depends_on` от панели. `compose down` проекта панели останавливает только панель.

### 4.2.1. Изоляция контейнеров

| Требование | Dashboard | Executor |
|---|---|---|
| UID:GID | `10001:10001` | `0:10001`; root нужен для файлов разных владельцев |
| Docker socket | Не монтируется | Единственный доступ к socket хоста |
| Служебная БД | Только своя БД пользователей/сессий | Приватная БД политик/операций |
| Игровые файлы, source workspaces, снимки, секреты | Не монтируются | Только утверждённые пути |
| Root filesystem | Read-only | Read-only |
| Linux capabilities | `drop: ALL` | `drop: ALL`; CHOWN/DAC_OVERRIDE/FOWNER для файлов, SETUID/SETGID для Git без root и KILL для завершения его процессов |
| Расширение привилегий | `no-new-privileges` | `no-new-privileges` |
| Host namespaces, privileged | Не используются | Не используются |

IPC-каталог принадлежит `root:10001`, имеет mode `0750`; Unix socket — `0660`, `root:10001`. Dashboard получает read-only mount каталога: он может подключаться к socket, но не заменять или удалять его. Executor имеет эксклюзивную блокировку владельца socket, корректно удаляет свой socket при остановке и восстанавливает подтверждённый устаревший socket после аварии. Живой executor или посторонний файл не удаляются.

Доступ к Docker daemon остаётся привилегией управления хостом. Контейнеризация не ослабляет требования проверки политик executor. Dashboard не получает Docker socket через общий volume, Docker credentials, rootfs хоста, каталоги `/proc`/`/sys` хоста или резервные копии executor.

В Compose задаются лимиты памяти/PID, ограниченная ротация stdout и tmpfs для временных файлов. Предел памяти процесса executor не ограничивает память дочерних контейнеров сборки Docker daemon: их ограничения проверяются отдельно.

### 4.2.2. Абсолютные host-пути

Docker daemon разрешает bind mounts относительно файловой системы своего хоста. Поэтому каталоги сервисов, source workspaces, executor state и подготовленных конфигураций видны executor под **теми же абсолютными путями**, что на хосте. Например, `/srv/ctf-manager/executor` монтируется в `/srv/ctf-manager/executor`, а `/srv/game-services` — в `/srv/game-services`. Подмена общего префикса на `/app/services` не допускается.

Произвольные корни добавляются сгенерированным Compose override. Монтирование `/` вместо явного списка корней запрещено. Сам каталог настроек можно монтировать в `/etc/ctf-manager`, поскольку его файлы не передаются Docker как bind-источники игровых контейнеров. Служебный executor state не пересекается с игровыми mounts или разрешёнными исходниками.

### 4.3. Сетевой доступ

Внутри контейнера dashboard слушает `0.0.0.0:8765`; Compose по умолчанию публикует порт только на `127.0.0.1:8765` хоста. Для доступа нескольких участников поддерживается привязка к явно выбранному приватному интерфейсу.

Поддерживаются два профиля:

- Локальный доступ через SSH-туннель: HTTP на loopback, отдельная документированная политика cookies для этого режима.
- Приватная сеть: HTTPS, `Secure` cookies, доверенный сертификат или явно настроенный TLS reverse proxy.

Для всех профилей обязательны `HttpOnly`, CSRF-защита изменяющих запросов, проверка допустимых Host/Origin и ограничения сессий. Заголовки reverse proxy доверяются только от настроенных адресов.

## 5. Основные сущности

### 5.1. Service

Зарегистрированный игровой сервис:

- Постоянный `service_id`, название и описание.
- Канонический путь существующего проекта и его активных управляемых файлов.
- Отдельный source workspace и правила соответствия его файлов активному дереву.
- Compose project name, project directory, порядок файлов `-f`, profiles и источники переменных окружения.
- Подтверждённая конфигурация запуска и её ревизия.
- Список Compose services и фактически найденных контейнеров.
- Роли компонентов: приложение, БД, кеш, вспомогательный компонент.
- Карта управляемых файлов и изменяемых хранилищ.
- Разрешённые build contexts, mounts и исключения из политики безопасности.
- Набор компонентов, затрагиваемых обычным обновлением.
- Настройки проверок, таймаутов и хранения.
- Текущий релиз, последний локально проверенный релиз, baseline.
- Выявленные зависимости и общие ресурсы с другими сервисами.

Service ID не должен зависеть от имени каталога или текущего container ID.

### 5.2. Snapshot

Копия выбранных файлов с manifest:

- `snapshot_id`, `service_id`, время и автор.
- Назначение: baseline, manual, candidate source или recovery.
- Относительные пути, типы файлов, размеры, хеши и поддерживаемые атрибуты.
- Правила включения/исключения и ревизия карты файлов.
- Происхождение и уровень согласованности снимка.
- Состояние: `creating`, `complete`, `invalid` или `deleting`.
- Причина закрепления и объём занимаемого места.

Снимок не получает признак исправности приложения только потому, что копирование завершилось успешно.

### 5.3. Release

Неизменяемое описание подготовленной версии:

- `release_id`, `service_id`, источник и автор.
- Ссылка на исходный snapshot и хеш итогового управляемого дерева.
- Для Git в MVP: URL/идентификатор репозитория, выбранный ref, точный commit SHA и подкаталог источников; credentials хранятся отдельно в vault и не входят в исходники/снимки.
- Для Overlay: идентификатор основы, SHA патча и перечень применённых изменений.
- Точные локальные image ID и, при наличии, registry digests для всех образов в плане переключения.
- Уникальные локальные теги, удерживающие нужные образы в хранилище Docker.
- Проверенная конфигурация запуска, ревизия политики, необходимые секреты по ссылкам на неизменяемые версии в хранилище executor.
- Ссылки на хранилища данных и декларация совместимости с их текущим состоянием.
- Результаты сборки и проверок.

Содержимое Release не изменяется. Новые результаты запуска и проверки сохраняются отдельными событиями. Удобные статусы вычисляются из этих событий: `prepared`, `active`, `locally_verified`, `failed`, `retired`.

Локальная проверка и ручное подтверждение пользователем имеют разное происхождение. Доступность отката определяется также наличием образов, конфигурации и секретов, а не только статусом релиза.

### 5.4. Operation

Фоновое задание:

- `operation_id`, тип, инициатор и ключ идемпотентности.
- Целевой сервис, релиз и ожидаемые ревизии конфигурации/файлов.
- Набор блокируемых ресурсов.
- Текущий этап, время, таймауты и запрошенная отмена.
- Предыдущее и желаемое состояние.
- Recovery point, если операция меняет работающий сервис.
- Журнал событий и диагностические сообщения.

## 6. Доверенные данные и файловое размещение

Пример размещения на Docker-хосте:

```text
/srv/ctf-manager/                 root:root 0755
  config/                        root:root 0700; только executor
    executor.json                root:root 0600
    compose.mounts.yaml          root:root 0600
    compose.env                  root:root 0600
  dashboard/                     10001:10001 0700
    dashboard.sqlite             пользователи и серверные сессии
  runtime/                       root:10001 0750
    executor.sock                root:10001 0660
  executor/                      root:root 0700; только executor
    executor.db                  сервисы, политики, операции, релизы
    snapshots/                   baseline, manual, recovery
    staging/                     подготовленные кандидаты
    releases/                    manifests и связанные артефакты
    secrets/                     защищённые секреты запуска
  exports/                       копии вне обоих state-каталогов
  services/                      необязательный корень новых проектов
  workspaces/                    исходники вне игровых mounts

/srv/game-services/              существующие проекты; отдельный approved root
/srv/ctf-workspaces/             существующие workspace; отдельный approved root
```

Dashboard видит только `dashboard/` как `/var/lib/ctf-manager` и `runtime/` как read-only `/run/ctf-manager`. Executor state и корни проектов сохраняют абсолютные host-пути внутри executor. Рабочие каталоги и состояние используют bind mounts и сохраняются при пересоздании контейнеров панели. `down -v` панели не является процедурой очистки или восстановления.

SQLite-файлы web и executor имеют разных владельцев. Web не может изменять доверенные записи executor прямым доступом к его БД. Изменения выполняются только через проверяемые операции протокола.

Пути и разрешённые корни обнаружения настраиваются локальным администратором до чтения игровых файлов через web. Web не может предложить executor прочитать произвольный новый корень. Служебные данные, снимки, staging и source workspaces должны находиться вне игровых mounts; служебные данные также находятся вне рабочих деревьев сервисов. Поддержка разных файловых систем должна учитывать, что перемещение между ними не является атомарным.

При нехватке разрешений регистрация или операция завершается понятной ошибкой. Панель не должна автоматически менять владельцев или права всего проекта ради получения доступа.

Обновление панели должно сопровождаться резервной копией её данных перед миграцией схемы. Резервирование работающей SQLite выполняется через согласованный механизм, например Online Backup API, а не обычным копированием одного `.db` файла.

## 7. Регистрация существующего сервиса

### 7.1. Поддерживаемый профиль Compose в MVP

MVP поддерживает ограниченный, документированный профиль Compose. Обнаруженный проект не считается автоматически пригодным для управляемого обновления.

| Особенность | Поведение MVP |
|---|---|
| Несколько контейнеров одного проекта | Поддерживаются, роли и цели обновления подтверждаются явно |
| Несколько Compose-файлов | Сохраняются порядок объединения и итоговая конфигурация |
| Profiles и env files | Сохраняются выбранные profiles и зарегистрированные источники переменных |
| Локальный Dockerfile и build context | Поддерживаются внутри разрешённых корней |
| Готовые образы | Регистрируются с точными локальными image ID |
| Bind mounts кода и конфигурации | Поддерживаются при явной карте путей, стабильных host paths и проверенном сценарии переключения |
| Named volumes с данными | Сохраняются по фактическим именам, содержимое не копируется и не откатывается |
| Существующие внешние сети | Используются по подтверждённой идентичности |
| Anonymous volumes со значимыми данными | Блокируют пересоздание до ручного перевода на поддерживаемое постоянное хранилище |
| Значимые данные в writable layer или tmpfs | Блокируют пересоздание, если их потеря не признана допустимой явно |
| Lifecycle hooks, удалённые build contexts, динамические include/extends | Не поддерживаются в MVP; требуется заранее подготовленная простая конфигурация |
| Привилегированный режим, host namespaces, devices, нестандартные mount drivers | Не поддерживаются в профиле MVP |

Подключение несовместимого проекта должно завершаться объяснением конкретной причины до первой изменяющей операции. Несовместимые особенности не должны молча отбрасываться.

Пути источников bind mounts и их предки не должны быть доступны для подмены из игровых mounts или web UID. Изменяемое содержимое каталога данных допускается, подмена его точки привязки — нет. Если это условие не выполняется, пересоздание блокируется до ручной подготовки безопасной структуры. Защита копирования файлов не заменяет эту проверку путей, передаваемых Docker.

### 7.2. Процедура регистрации

1. Admin нажимает «Добавить сервис» и выбирает папку существующего Compose-проекта в GUI либо вводит её абсолютный путь внутри заранее подключённых корней. Панель показывает разрешённые корни; source workspace выбирается автоматически внутри разрешённого workspace root.
2. Executor читает контейнеры Docker и допустимые файлы выбранного проекта; значения секретов в web не раскрываются.
3. Панель показывает предполагаемое соответствие проекта и контейнеров; совпадение только по имени недостаточно.
4. Сохраняются исходный Compose project name, project directory, порядок файлов, profiles и источники окружения.
5. Формируется нормализованная конфигурация с абсолютными разрешёнными путями.
6. Администратор классифицирует компоненты, данные, mounts и цели обычного обновления.
7. Панель показывает конфликтующие регистрации и общие ресурсы.
8. Нормализованный план сверяется с фактическим Docker inspect всех целей: image ID, environment, command/entrypoint, mounts, порты, сети и ограничения. Расхождения разрешаются явно; существенные ручные изменения кода/config внутри writable layer блокируют пересоздание до подготовки воспроизводимой версии.
9. Web Admin просматривает неизменяемую заявку и подтверждает её в панели по `proposal_id` и digest. Executor повторно проверяет фактический runtime, пути, ограничения профиля и конфликты. Изменение просмотренного объекта требует новой заявки. CLI для подтверждения не требуется; повтор того же подтверждения возвращает тот же сервис и продолжает незавершённую инициализацию без дублирования регистрации.
10. Создаются baseline управляемых файлов и запись первоначального импортированного релиза с сохранением существующих образов и версий секретов. Source workspace инициализируется копией управляемых исходников без изменения активного проекта.
11. Проверяется полнота артефактов точки возврата. Только после этого разрешается первое управляемое пересоздание приложения.

Мастер позволяет проверить название, роли компонентов, цели обновления, управляемые пути и классификацию хранилищ без ручного редактирования JSON. Неоднозначные mounts и writable layer не считаются автоматически безопасными: Admin должен подтвердить классификацию, неподдерживаемый профиль блокируется. Ошибка создания workspace или baseline после принятия заявки отображается отдельно от факта регистрации; повтор инициализации не перезапускает игру. Необязательный Git-источник настраивается в мастере или позднее в карточке сервиса.

Выбор папки открывает только заранее разрешённые discovery roots на Docker-хосте, а не файловую систему браузера. Просмотр выполняет executor через типизированный запрос Admin с CSRF; dashboard не получает mount игровых каталогов. Доступны переходы вниз/вверх в пределах корня, возврат к списку корней, обновление, выбор текущей папки и ручной ввод. Символические ссылки и переходы вне корней отклоняются, включая подмену во время открытия. Листинг ограничивается 4096 просмотренными записями, 256 каталогами и 64 КиБ имён/путей; усечение сообщается явно. Имена четырёх стандартных Compose-файлов служат подсказкой без чтения содержимого. Выбор пути не запускает контейнеры, не регистрирует сервис и не заменяет последующую проверку Docker/Compose; прежние ответы после смены папки или обновления не могут подставить устаревший путь.

Локальная настройка установки остаётся необходимой для подключения новых host-корней и создания первого Admin. Это не часть регистрации каждого сервиса: внутри уже подключённых корней весь цикл добавления и подтверждения выполняется через веб.

Регистрация и создание baseline не перезапускают контейнеры. Импортированный релиз помечается как импортированный; полнота его артефактов и результат проверки текущего экземпляра отображаются отдельно. Реальная воспроизводимость запуска считается проверенной только после контролируемого повторного запуска, а не по одному inspect. Baseline отражает состояние на момент регистрации и не считается доказанной оригинальной версией организаторов.

Повторная регистрация того же Compose project или пересекающихся управляемых деревьев как независимых сервисов запрещается. Общие постоянные хранилища допускаются только как явно зарегистрированная зависимость с общей блокировкой конфликтующих операций.

### 7.3. Карта файлов и состояния

Для каждого сервиса обязательны следующие категории:

| Категория | Пример | Поведение |
|---|---|---|
| Управляемый код | `src/`, `app/`, Dockerfile | Снимки, сборка, применение и восстановление |
| Управляемая конфигурация приложения | Проверенный `config.yaml` | Версионируется по явному правилу |
| Доверенная конфигурация запуска | Нормализованный Compose | Хранится у executor, обычный Deploy её не расширяет |
| Секреты | Зарегистрированные env/secret sources | Неизменяемые версии у executor и ссылки в релизах |
| Постоянные данные | БД, uploads, флаги, игровые аккаунты | Сохраняются между релизами |
| Временные данные | Кеши и временные файлы | Допустимость потери подтверждается при регистрации |
| Исключённые данные | `.git/`, логи, артефакты, вложенные mounts | Не включаются в build context и снимки кода автоматически |

Правила категорий не должны противоречить друг другу. Известный mount без классификации блокирует пересоздание. Полноту карты значимых данных подтверждает администратор: обнаружение mounts не доказывает отсутствие данных внутри приложения.

Панель не должна автоматически переносить игровые данные между хранилищами. Если требуется миграция данных из writable layer или anonymous volume, администратор выполняет её отдельной процедурой до включения управляемого пересоздания.

Для MVP значения секретов и необходимые env-входы импортируются в защищённые неизменяемые версии у executor. Релиз ссылается на точную версию; изменение файла по исходному пути не меняет старый релиз. Новые версии, отзыв и удаление — отдельные операции с показом зависимых релизов. Нужные версии удерживаются вместе с релизами, если не отозваны явно. Живые изменяемые внешние secret paths не входят в гарантированный профиль отката MVP.

## 8. Подготовка кандидата и сборка

### 8.1. Источник и согласованность

Участник выбирает зарегистрированный сервис и запускает подготовку из его source workspace. Executor сам определяет допустимые пути и их соответствие активным файлам по доверенной политике; HTTP-запрос не задаёт произвольный путь источника.

Кандидат копируется в отдельный staging, недоступный на запись web-процессу и игровым контейнерам. Формируются manifest и хеш дерева. После завершения подготовки содержимое кандидата фиксируется; дальнейшее изменение исходного каталога не меняет подготовленный релиз.

Изменение читаемого файла во время копирования должно обнаруживаться и приводить к повторной подготовке или отказу. Обычное последовательное копирование дерева не объявляется атомарным снимком всех файлов на один момент времени. Для исходников предусматривается согласованная работа команды без параллельного редактирования во время подготовки; уровень согласованности сохраняется в manifest.

Изменения source workspace являются ожидаемой работой над кандидатом и не считаются drift активного релиза. Изменение workspace после подготовки не изменяет уже зафиксированный кандидат и показывается как наличие новых неподготовленных правок. Прямое редактирование активного дерева через SSH или игровой mount является отдельным drift; подготовка и сборка панели в него не записывают.

### 8.2. Предпросмотр

До сборки и применения пользователь видит:

- Добавленные, изменённые и удаляемые управляемые файлы.
- Отличия от активного релиза и обнаруженные внешние изменения.
- Список собираемых образов и предполагаемых пересоздаваемых контейнеров.
- Компоненты и хранилища, которые затронет операция.
- Проверки, таймауты и требования совместимости с данными.
- Наличие доступной точки возврата и объём требуемого дискового пространства.

Операция связывается с точными ревизиями кандидата, политики и активного состояния. При их изменении ранее показанный план признаётся устаревшим и применение требует нового плана. Значения секретов в diff скрываются.

### 8.3. Сборка

1. Проверить карту путей, политику сборки, зависимости и лимиты.
2. Сформировать build context только из разрешённых файлов и зарегистрированных входов.
3. Собрать новый образ без изменения тегов действующего релиза.
4. Присвоить образу уникальный локальный тег релиза и сохранить точный image ID.
5. Проверить полноту артефактов, конфигурацию запуска и наличие точки возврата. Проверить runtime-настройки образа, включая `Config.Volumes`: новый volume без соответствующего зарегистрированного mount блокирует релиз, чтобы не создавать неучтённое anonymous-хранилище.
6. Создать неизменяемую запись подготовленного Release.

Сборка не должна включать по умолчанию игровые данные, Git credentials, служебные каталоги панели и секреты. Передача build secrets или дополнительных contexts допускается только по явно зарегистрированной политике; host entitlements в MVP запрещены.

Build context формируется по manifest с нужными исходными правами файлов, включая executable bit. Сохранение этих атрибутов в контексте не должно менять владельца защищённого staging на исходного пользователя.

Команды Dockerfile выполняются только штатным изолированным builder. Произвольные host-side hooks отсутствуют. Запуск CLI выполняется без shell-интерполяции, с фиксированным исполняемым файлом и контролируемым окружением.

Build создаёт артефакты и не переключает контейнеры. В MVP допускается ручное применение только подготовленного релиза. Если для сетевой сборки нет нужных зависимостей, подготовка завершается ошибкой, действующий экземпляр не меняется.

## 9. Применение релиза

### 9.1. Предварительные условия

Перед переключением executor должен:

1. Захватить блокировки сервиса и всех конфликтующих ресурсов.
2. Проверить соответствие фактических контейнеров, mounts и активных файлов зарегистрированному состоянию.
3. Проверить ревизии кандидата и политики, наличие образов и точных неотозванных версий секретов.
4. Проверить свободное место и доступность recovery point.
5. Проверить заявленную совместимость релиза с текущими данными.
6. Сохранить долговечное намерение операции и точку возврата до первого изменения активного состояния.

Обнаруженный drift активного состояния отображается пользователю и блокирует автоматическое продолжение до разрешения конфликта. Изменения разрешённых активных файлов можно явно принять как новую непроверенную recovery point после просмотра diff; это создаёт новый план с текущими хешами, но не объявляет состояние исправным. Изменение состава контейнеров, mounts или прав запуска требует локального обновления доверенной политики. Неизвестные ручные исправления молча не перезаписываются.

### 9.2. Переключение

1. Подтвердить готовность неизменяемого кандидата.
2. Остановить только необходимые компоненты приложения в соответствии с планом.
3. Применить управляемые файлы, если они используются через bind mounts или должны быть возвращены в рабочее дерево.
4. Пересоздать выбранные контейнеры с образами подготовленного релиза и подтверждённой конфигурацией.
5. Сохранить идентификаторы фактически созданных контейнеров и наблюдаемую активную версию до получения результата healthcheck. При частичном переключении показывать версии по компонентам и незавершённое состояние сервиса.
6. Дождаться прогрева и выполнить предусмотренные проверки.
7. Отдельно зафиксировать результаты проверок, итог операции и длительность простоя. Неуспешный healthcheck не должен оставлять прежний релиз в UI как активный, если фактически уже запущен новый.

Применение файлов учитывает добавления, изменения и удаления внутри управляемого набора. Неуправляемые файлы и постоянные данные сохраняются. Подмена всего каталога проекта допустима только для профиля, в котором доказано отсутствие сохраняемых данных и учтено поведение bind mounts.

Простая замена каталога или символической ссылки не считается гарантией обновления существующего bind mount. Поддерживаемые сценарии должны проверяться с фактическим пересозданием нужных контейнеров.

Запуск подготовленного релиза использует сохранённые локальные образы и не выполняет неявные build/pull. Конфигурация Compose генерируется или читается из доверенного хранилища executor; игровые Compose-файлы и `.env` повторно не интерпретируются во время переключения.

Вызов Compose должен явно ограничиваться выбранными компонентами и исключать неявное изменение зависимостей. Фактические побочные действия проверяются по Docker; одного предварительного списка целей в UI недостаточно.

### 9.3. Сохранение данных и зависимости

Постоянные volumes и bind mounts данных используются под прежними фактическими идентификаторами. Их содержимое не откатывается вместе с приложением.

БД, кеши и другие зависимости не пересоздаются обычным Deploy приложения, если это не входит в явно показанный план. Изменение состава проекта или политики запуска является отдельной административной процедурой.

В автоматических операциях запрещены удаление volumes, обновление anonymous volumes, удаление неизвестных orphan-контейнеров и глобальный Docker prune.

Изменения схемы БД не выполняются панелью как отдельный шаг MVP. Сервисы с автоматическими миграциями при старте требуют явного подтверждения совместимости; потенциально необратимое изменение данных блокирует обычный сценарий с обещанием быстрого отката и выполняется по отдельной документированной процедуре.

### 9.4. Ошибки и отмена

Ошибка до переключения завершает подготовку без изменения активного экземпляра. Ошибка после начала переключения фиксирует фактическое состояние, сохраняет recovery point и предоставляет действие восстановления.

Отмена подготовки разрешена до изменения активного состояния. После начала переключения кнопка отмены означает запрос безопасного завершения текущего шага и возврата по заранее определённой политике компенсации; она не должна произвольно убивать процесс посреди изменения файлов. `cancelled` после переключения допускается только после подтверждённого возврата. Если безопасный возврат не определён или не завершён, используется `requires_recovery`; фактически активная версия показывается во всех случаях.

Автоматический компенсирующий возврат при ошибке переключения допускается только там, где заранее определено безопасное поведение. Автоматический откат по неуспешному функциональному healthcheck не входит в MVP.

## 10. Откат и аварийное восстановление

### 10.1. Быстрый Rollback

Пользователь выбирает сохранённый релиз. Панель показывает время, источник, результаты проверок, изменения и пригодность релиза для запуска с текущими данными.

Executor должен:

1. Проверить manifest, локальные образы, конфигурацию и точные неотозванные версии секретов.
2. Проверить выбранный план против текущей доверенной политики, совместимость с хранилищами и отсутствие неразрешённого drift. Историческая ревизия политики не позволяет вернуть отменённые привилегии.
3. Зафиксировать операцию и защитить текущее состояние recovery point.
4. Остановить нужные компоненты приложения, затем восстановить управляемые файлы выбранного релиза, сохранив игровые данные.
5. Пересоздать только выбранные компоненты из сохранённых локальных образов и зафиксировать фактически активную версию.
6. Выполнить проверки и отдельно зафиксировать их результат. Используется тот же протокол переключения и аварийной сверки, что и для Deploy.

Rollback не вызывает сборку, pull или обращение к Git. Если нужные артефакты отсутствуют, панель сообщает, что быстрый откат недоступен, до остановки сервиса.

Доступность локальных образов не гарантирует совместимость старого кода с изменёнными данными. Такая совместимость задаётся и проверяется отдельно.

### 10.2. Восстановление Snapshot и Baseline

Снимок файлов без готовых образов можно восстановить как новый кандидат, затем собрать и применить обычным процессом. Это отдельное действие, которое не называется быстрым Rollback.

Baseline защищён от обычного удаления и перезаписи. При регистрации сохраняется также импортированный релиз с исходными образами. Его пригодность для аварийного запуска проверяется отдельно от целостности baseline.

Полное восстановление каталога с игровыми данными не входит в MVP. Интерфейс не должен предлагать действие, которое обещает сохранить данные при отсутствии соответствующего поддерживаемого сценария.

### 10.3. Аварийный CLI

Локальный CLI должен предоставлять:

- Состояние executor, сервисов и активных операций.
- Список сохранённых релизов и причин недоступности отката.
- Запуск возврата выбранного релиза.
- Просмотр и продолжение предусмотренного восстановления незавершённой операции.
- Проверку окружения и экспорт состояния панели.

CLI использует тот же executor, блокировки, проверки и журнал. При недоступном executor локальный администратор сначала запускает его или использует документированную ручную процедуру; второй независимый движок изменения сервисов не создаётся.

## 11. Снимки, целостность и хранение

### 11.1. Создание снимка

Копирование выполняется во временный каталог. После проверки manifest, хешей и необходимых атрибутов снимок получает состояние `complete`. Незавершённый снимок не доступен как точка восстановления.

Для управляемых файлов сохраняются числовые UID/GID, mode, содержимое и символьные ссылки в пределах поддерживаемой политики. Исходные владельцы и права хранятся как метаданные manifest; сами snapshot/staging принадлежат executor с нормализованными защищёнными правами. Исходные атрибуты применяются только при восстановлении в разрешённое активное дерево. Нужные дополнительные атрибуты выявляются при регистрации. Если обязательные атрибуты не поддерживаются, операция должна завершаться ошибкой до изменения сервиса.

Символьные ссылки сохраняются как ссылки и не обходятся при копировании. Выход ссылок за разрешённые корни, специальные файлы, вложенные mount points, setuid/setgid и file capabilities обрабатываются по явной политике; небезопасные варианты не принимаются молча. Для рабочего staging не используются hardlinks к активным файлам.

Целостность файлового снимка не равна согласованности работающей БД. В MVP снимки охватывают только зарегистрированные управляемые файлы.

### 11.2. Политика по умолчанию

| Категория | Правило |
|---|---|
| Baseline | Один исходный снимок, без автоматической перезаписи и удаления |
| Первоначальный импортированный релиз | Закреплён по умолчанию вместе с исходными образами и конфигурацией; работоспособность и полнота артефактов имеют отдельные статусы |
| Активный релиз | Сохраняются manifest, необходимые файлы, конфигурация и образы |
| Предыдущие проверенные релизы | Три предыдущих релиза с успешной локальной проверкой; происхождение проверки видно |
| Последний пригодный проверенный релиз | Закрепляется независимо от обычной ротации |
| Manual snapshots | Отдельная очередь, по умолчанию три последних снимка |
| Recovery активной операции | Закрепляется до подтверждённого завершения или восстановления |
| Неудачные и неиспользованные кандидаты | Ограничение по объёму и сроку хранения |

Один физический снимок или образ может использоваться несколькими объектами. Удаление выполняется только после проверки всех ссылок и закреплений. Неудачный кандидат и ручной снимок не вытесняют проверенный релиз.

Количество объектов дополняется квотой в байтах. Перед операцией проверяется место на файловых системах staging, снимков и Docker storage, а также запас inode. Если новая операция не помещается без удаления защищённых объектов, она отклоняется до переключения.

Сборщик мусора панели работает только со своими зарегистрированными объектами. Общие и внешние образы не удаляются. Используемые образы удерживаются уникальными тегами и ссылками в реестре; внешняя очистка Docker обнаруживается как потеря артефактов.

### 11.3. Резервирование панели

Экспорт должен включать согласованные БД панели, конфигурацию, политики сервисов и manifests релизов. Обычный экспорт не содержит открытых секретов: чувствительные значения заменяются ссылками во всех включённых конфигурациях, включая раскрытый Compose environment, а не только исключаются из каталога secrets. После восстановления сессии аннулируются; экспорт хранится с ограниченным доступом. Без защищённого резервирования секретов восстановление авторизованных подключений и некоторых релизов может потребовать их повторного ввода; это показывается в составе экспорта.

Локальные снимки и экспорт не защищают от потери диска или root-доступа атакующего. Вынос копий на другой хост является последующей возможностью.

### 11.4. Реализация администрирования хранения

Локальная секция `storage` в bootstrap задаёт отдельные count/age лимиты manual/candidate и byte quotas snapshots/staging/всего state/Docker. Значения по умолчанию и единицы описаны в [политике хранения](storage.md). Незавершённые allocations учитываются в квоте и очищаются только по durable receipts после завершения owning job. Сначала сохраняется tombstone; физическое удаление проверяет владение/типы/mount и возобновляется через приватный trash. Tombstone блокирует новые ссылки до завершения удаления. Shared/external Docker-артефакты и общий build cache не удаляются.

Физическое free-space/inode измерение Docker storage допускается только по явно добавленному readonly data-root bind, сверяемому с daemon. Без этого источника физическая ёмкость Docker обозначается как неизвестная, а логический budget Engine остаётся активен. Другой `/` или общая цифра внутри executor не выдаются за host storage. Runtime limits являются preflight-проверками, а не kernel reservations BuildKit.

`backup`/`restore` — локальные административные команды вне Web. Перед backup оба процесса панели останавливаются, exclusive maintenance locks фиксируют отсутствие writers обеих БД; согласованные SQLite копии создаются через `VACUUM INTO`. Обычный режим — очищенный каталог метаданных, который требует повторной локальной проверки регистрации и явно перечисляет отсутствующие секреты/исходники/конфигурацию/images. Для рабочего восстановления применяется `protected_full`: весь архив, включая vault и снимки, шифруется AES-256-GCM с Argon2id и аутентифицированным окончанием потока. Фраза вводится из приватного файла/stdin и не передаётся аргументом.

Restore разрешён только в новый каталог, проверяет hashes/пути/типы/лимиты, отзывает сессии и старые recovery approvals, отменяет queued jobs, переводит running в interrupted и сохраняет unresolved locks. Перезапуск старых действий и пересоздание игровых контейнеров не выполняются автоматически. Docker images и игровые данные не входят в копию панели. Точная процедура и границы [описаны отдельно](backup.md).

## 12. Операции, блокировки и восстановление после сбоев

### 12.1. Очередь и идемпотентность

Все длительные действия выполняются фоновыми заданиями. HTTP API возвращает идентификатор созданной операции, а не удерживает запрос до окончания сборки или переключения.

Для изменяющего запроса обязателен ключ идемпотентности. Повтор с тем же ключом, инициатором и теми же параметрами возвращает прежнюю операцию. Использование ключа с другими параметрами отклоняется. Срок хранения такого соответствия документируется и составляет не менее срока хранения операции.

Потеря соединения, HTTP-ответа или таймаут клиента не создают новую операцию и не доказывают, что предыдущая не выполнилась.

### 12.2. Блокировки

В один момент допускается одна изменяющая операция для одного сервиса. Дополнительно блокируются реальные конфликтующие ресурсы: Compose project, пересекающиеся управляемые каталоги, переключаемые контейнеры и общие ресурсы по карте зависимостей.

Наличие общего volume само по себе не требует блокировать весь мониторинг или копирование независимого кода. Эксклюзивность определяется типом операции и тем, может ли она затронуть общий ресурс.

Порядок захвата нескольких блокировок фиксирован для исключения взаимной блокировки. CLI и Web используют одну очередь executor. Пользователь видит ожидаемую операцию, занятой ресурс и владельца блокировки.

По умолчанию одновременно выполняется одна Docker-сборка. Лимиты сборок, копирования и переключений настраиваются независимо. Приоритет аварийного отката выше очереди новых сборок, но он не прерывает небезопасно уже начатое переключение.

### 12.3. Состояния задания

| Состояние | Значение |
|---|---|
| `queued` | Принято и ожидает ресурсов |
| `running` | Выполняется известный этап |
| `succeeded` | Фактический результат проверен и зафиксирован |
| `failed` | Ошибка с определённым фактическим состоянием и сохранённым путём дальнейших действий |
| `cancelled` | Отменено до изменения активного состояния либо после подтверждённого возврата к состоянию до переключения |
| `interrupted` | Обнаружено прерывание; выполняется сверка состояния |
| `requires_recovery` | Автоматически подтвердить безопасное конечное состояние невозможно |

Название текущего этапа хранится отдельно от состояния задания: проверка, копирование, сборка, создание recovery point, переключение, прогрев, функциональная проверка, фиксация результата.

### 12.4. Долговечность и сверка

Намерение каждого изменяющего шага сохраняется до обращения к Docker или изменения файлов. После выполнения сохраняется наблюдаемый результат. Связь операций с созданными контейнерами и артефактами позволяет найти результат после потери ответа.

Критический журнал executor использует настройки долговечности SQLite, соответствующие подтверждённой записи намерения до изменения, по умолчанию WAL с `synchronous=FULL`. Готовность файловых артефактов фиксируется только после записи содержимого, manifest и необходимых синхронизаций файлов/каталогов. Буферизация диагностических логов не подменяет критический журнал.

После старта executor должен:

1. Найти незавершённые операции и временные объекты.
2. Сопоставить журнал с фактическими файлами, образами и контейнерами.
3. Определить, какие шаги уже завершены, а какие не начинались.
4. Подтвердить завершение, выполнить предусмотренное безопасное восстановление или выставить `requires_recovery`.
5. Заблокировать конфликтующие новые изменения до разрешения неопределённости.

Нельзя считать совместную операцию над SQLite, Docker и файловой системой единой ACID-транзакцией. Каждый шаг должен иметь проверяемое повторение или процедуру компенсации. Слепой повтор всего Deploy после перезапуска запрещён.

Доступный после сбоя recovery point не удаляется ротацией. Очистка временных файлов выполняется только после сверки их принадлежности операциям.

### 12.5. Ошибки инфраструктуры

Обязательна обработка потери Docker API, рестарта Docker daemon, исчезновения контейнера, ENOSPC, исчерпания inode, ошибки доступа и внезапного завершения executor.

Ошибка записи журнала до изменения активного состояния останавливает операцию. Ошибка записи после фактического изменения переводит её в режим сверки; UI не показывает успешный результат только на основании успешного вызова Docker CLI.

## 13. Проверки работоспособности

### 13.1. Независимые сигналы

| Сигнал | Что означает |
|---|---|
| Container state | Контейнер существует и имеет наблюдаемое состояние Docker |
| Docker healthcheck | Результат встроенной проверки, если она определена |
| Readiness | Зарегистрированный TCP/HTTP endpoint готов принимать обращения |
| Local functional check | Проверен заданный сценарий приложения |
| Manual confirmation | Участник явно подтвердил работоспособность с комментарием |
| External checker | Результат организаторов, если настроена интеграция после MVP |

Каждый сигнал содержит источник, время, срок актуальности и диагностическую причину. Отсутствующая проверка отображается как `not configured`, недоступная — как `unknown`, устаревшая — как `stale`. Эти состояния не заменяются зелёным статусом.

Успешная локальная проверка не обозначается как гарантированный успешный checker организаторов. В MVP поле внешнего checker показывает отсутствие интеграции, а не предполагаемый результат.

HTTP/TCP-проверки выполняются в сетевом namespace executor. В основном Compose-профиле это bridge: `127.0.0.1` означает сам executor, а не vulnbox. При регистрации нужно подтвердить адрес, доступный из executor (например, уже опубликованный приватный адрес хоста). Host-only loopback endpoint нельзя считать доступным через Docker gateway. Панель не меняет игровые port bindings ради проверки; если подходящего маршрута нет, проверка остаётся не настроенной/недоступной до отдельного административного решения.

### 13.2. Проверки MVP

Поддерживаются ограниченные типизированные проверки:

- TCP connect к зарегистрированному адресу/порту.
- HTTP-запрос с проверкой кода и ограниченного по размеру ответа.
- Ограниченная последовательность HTTP-действий для функционального сценария.

Цели проверок и допустимые сетевые адреса подтверждаются в политике сервиса. Произвольный shell-скрипт с правами хоста не является способом задания проверки.

Для функционального сценария задаются безопасные тестовые данные, ограничения побочных эффектов и процедура очистки. Проверка не должна удалять или заменять игровые флаги. Секреты проверок скрываются в интерфейсе и логах.

Настраиваются время прогрева, таймаут одного запроса, общий срок проверки и ограниченное число попыток. Для сервиса без поддерживаемой функциональной проверки допускается ручное подтверждение; происхождение такого результата отображается явно, а гарантия автоматической проверки отсутствует.

### 13.3. Автоматический откат после MVP

Перед включением этой функции требуется отдельная политика: какие ошибки её запускают, сколько попыток допустимо, какой релиз выбран и почему он совместим с текущими данными. Переключение релизов по кругу запрещается.

Отсутствие результата checker, временная недоступность внешней зависимости или одна ошибка в период прогрева не должны автоматически считаться доказанной неисправностью нового релиза.

## 14. Управление, логи и метрики

### 14.1. Действия над сервисами

| Действие | Семантика |
|---|---|
| Start | Запуск существующих остановленных подтверждённых контейнеров |
| Stop | Остановка выбранных контейнеров с зарегистрированным таймаутом |
| Restart | Перезапуск существующих контейнеров без применения новой конфигурации |
| Prepare | Создание неизменяемого кандидата и diff |
| Build | Сборка кандидата и создание подготовленного релиза |
| Deploy | Применение выбранного подготовленного релиза |
| Snapshot | Копия управляемых файлов без утверждения об исправности |
| Rollback | Применение сохранённого релиза без сборки и загрузки образов |
| Recover | Предусмотренное восстановление прерванной операции |

Если контейнер удалён, Start не должен молча создавать новый экземпляр по текущим файлам проекта. Для создания используется явный запуск сохранённого релиза с теми же проверками, что и Deploy.

### 14.2. Логи

В MVP обязательны:

- stdout/stderr выбранного контейнера и объединённый поток сервиса.
- Live-режим, пауза, ограниченная загрузка предыдущих строк и фильтр времени.
- Текстовый поиск, include/exclude regex и подсветка совпадений.
- Отдельные журналы подготовки, сборки, переключения и восстановления.
- Автоматическое переподключение к новым container ID после пересоздания.

Доступность прошлых контейнерных логов зависит от logging driver и существования контейнера. Панель показывает ограничения драйвера. Долговечное полное архивирование контейнерных логов не входит в MVP; журналы собственных операций сохраняются независимо от жизненного цикла контейнеров.

Каждая запись содержит время, источник, container ID или operation ID. Неполный поток и отброшенные записи отмечаются явно. Порядок объединённого вывода не объявляется точным глобальным порядком событий разных контейнеров.

Regex обрабатываются ограниченным движком Go `regexp`; ограничиваются длина шаблона, строки и обрабатываемый объём. Для медленного клиента используются ограниченный буфер и backpressure. Исчерпание буфера не должно блокировать Docker или игровой сервис.

Содержимое логов, имена файлов, diff и будущие сетевые данные отображаются как текст без исполнения HTML. Управляющие последовательности обрабатываются безопасно. Известные секреты редактируются по заданным правилам, но логи и PCAP всё равно считаются чувствительными данными.

### 14.3. Метрики MVP

Для хоста: CPU, RAM, swap, load average, uptime, свободные байты и inode на используемых файловых системах, сетевые счётчики.

Для контейнера: состояние, CPU, RAM, сетевые счётчики, block I/O, число процессов, события OOM/restart и доступные лимиты.

Контейнерные `/proc` и `/sys` не объявляются метриками хоста. Источник каждой host-метрики фиксируется и проверяется на Linux-стенде; нужные read-only mounts добавляются только executor и отдельно документируются. Для host-метрик не включаются privileged, host PID/network namespaces или mount всего `/`. Если безопасный источник отсутствует, метрика недоступна.

Показатели агрегируются по сервису с учётом общих namespaces и особенностей измерений. Единицы CPU явно подписываются: для хоста — процент суммарной мощности всех ядер, для контейнера — процент одного ядра. Недоступная метрика показывается как недоступная, а не как ноль.

По умолчанию сбор выполняется раз в 5 секунд. MVP хранит ограниченную историю последних 60 минут и показывает график последних 15 минут. Длительная история и downsampling добавляются после MVP.

История MVP находится в RAM executor: не более 721 точки на ряд, с отсечением по времени; перезапуск очищает историю и сообщает новое время её начала. График позволяет выбрать 15 или 60 минут и сохраняет разрывы наблюдений. Ответ API содержит последний срез всех зарегистрированных компонентов и историю одного выбранного компонента, чтобы ограничить размер ответа. Host CPU измеряется относительно всех ядер, container CPU — относительно одного ядра. В Compose host-источники включаются флагом bootstrap `--host-metrics`: пять отдельных read-only procfs файлов, проверяемых executor. Сеть берётся из namespace host PID 1; filesystem capacity — из уже разрешённых host-путей. Подробная схема приведена в [описании метрик](metrics.md).

Сбор выполняется независимо от числа открытых вкладок: новые клиенты получают существующий поток измерений, а не создают собственные опросы Docker.

## 15. Авторизация, роли и границы безопасности

### 15.1. Роли

| Возможность | Admin | Defender | Viewer |
|---|---|---|---|
| Состояние сервисов и метрики | Да | Да | Да |
| Разрешённые логи, diff и история | Да | Да | Да |
| Start/Stop/Restart | Да | Да | Нет |
| Prepare/Build/Deploy | Да | Да | Нет |
| Snapshot/Rollback/Recover | Да | Да | Нет |
| Управление пользователями и сессиями | Да | Нет | Нет |
| Настройки UI и хранения в пределах политики | Да | Нет | Нет |
| Подготовка изменения регистрации/политики | Да | Нет | Нет |
| Подтверждение новой регистрации в разрешённых корнях | Через панель | Нет | Нет |
| Настройка Git URL и credentials | Да | Нет | Нет |
| Получение кандидата из настроенного Git-источника | Да | Да | Нет |
| Подключение новых host-корней и изменение профиля привилегий executor | Только локальный администратор ОС при настройке установки | Нет | Нет |

Разрешения проверяются сервером на каждом запросе, включая WebSocket. Viewer с доступом к логам или diff может видеть чувствительные игровые сведения; выдача этих разрешений должна быть явной. Разграничение доступа к отдельным сервисам можно добавить после MVP.

### 15.2. Учётные записи и сессии

- Пароли хешируются Argon2id с параметрами, подходящими целевой среде.
- Сессии хранятся на сервере, имеют ограниченный срок и могут быть отозваны.
- На сервере хранятся хеши session tokens; при восстановлении БД ранее выпущенные сессии аннулируются.
- Обязательны CSRF-защита, ограничения входа и смена session ID после авторизации.
- Только Admin создаёт пользователей и назначает роли.
- Изменение роли и блокировка пользователя прекращают недопустимый дальнейший доступ, включая открытые потоки.
- Пароли, session tokens, Git credentials и секреты не попадают в аудит и URL.
- TOTP допускается как последующее расширение.

### 15.3. Протокол executor

Web передаёт тип операции, зарегистрированный `service_id`, идентификаторы кандидата/релиза, ожидаемую ревизию и сведения об инициаторе. Executor сам получает пути, конфигурацию, образы и ограничения из доверенного реестра.

Протокол не принимает произвольные команды, аргументы Docker/Compose, пути восстановления или пользовательский manifest как готовую привилегированную инструкцию. Для регистрации предусмотрены отдельные типизированные методы обнаружения, подготовки заявки и подтверждения по digest. Указанный пользователем путь является недоверенным вводом, который executor проверяет по заранее заданным корням и профилю. Новые host-корни и расширение профиля привилегий через веб не разрешаются.

Unix socket защищён файловыми разрешениями и проверкой peer credentials. Dashboard проверяет сессию, роль Admin и CSRF перед регистрацией/настройкой источника и сам задаёт инициатора. Executor самостоятельно проверяет допустимость каждой заявки и не считает JSON от dashboard доверенной политикой без валидации и подтверждения.

Компрометация web UID не должна позволять выйти за bootstrap-корни, обойти поддерживаемый профиль или записать произвольный файл на хосте через executor. Web Admin и скомпрометированный процесс dashboard теперь могут инициировать регистрацию допустимых проектов внутри этих корней; отдельного обязательного OS-подтверждения на каждый сервис нет. Это осознанная граница доверия веб-регистрации и не является гарантией от уязвимостей Docker, ядра или самих зарегистрированных сервисов.

### 15.4. Недоверенные файлы и параметры

Executor не доверяет игровым Compose-файлам, `.env`, Dockerfile, путям и manifests, полученным от web. Он формирует собственный план по зарегистрированной политике и повторно проверяет целостность staging перед применением.

Файловые операции должны оставаться внутри разрешённых корней при конкурентной подмене путей и symlinks. Однократная проверка `realpath` перед последующей записью не считается достаточной защитой. Восстановление снимка не должно позволять запись за пределы управляемого набора.

Расширение mounts, сетевых прав, capabilities, устройств, build contexts, источников секретов и состава управляемых компонентов требует новой ревизии доверенной политики. Обычный Deploy меняет только разрешённое содержимое приложения и выбранные образы.

### 15.5. Аудит

Записываются входы, ошибки авторизации, изменение пользователей, запросы изменяющих операций, принятие политик, подготовка/применение релизов, восстановление, ротация и экспорт.

Событие содержит время UTC, инициатора, действие, целевые идентификаторы, результат и ссылку на операцию. UI показывает время в выбранном часовом поясе и сохраняет возможность просмотра UTC.

Аудит web и executor различает заявленного пользователя панели и локальную идентичность процесса/администратора ОС. Локальный аудит не объявляется защищённым от root на хосте.

## 16. Веб-интерфейс MVP

### 16.1. Dashboard

- Состояние хоста, свободное место и inode, ошибки Docker/executor.
- Список сервисов с раздельными состояниями контейнеров и проверок.
- Активный релиз, источник, наличие drift и доступного отката.
- Выполняющиеся и ожидающие операции, последние ошибки.
- Предупреждения о неопределённом состоянии, потере артефактов и неподдерживаемой конфигурации.

Dashboard не показывает единый зелёный `Healthy`, если известны только запущенные контейнеры.

### 16.2. Страница сервиса

Вкладки: Overview, Releases, Files/Diff, Snapshots, Logs, Operations, Metrics, Settings.

Главные действия: Prepare, Build, Deploy prepared release, Rollback. Start/Stop/Restart доступны отдельно. На каждой кнопке понятна цель: конкретный компонент или подтверждённая группа.

Для релиза показываются image ID, хеш дерева, время подготовки/применения, автор, локальные проверки, ручные подтверждения и доступность возврата. Для снимка явно указано, что это копия файлов, а не гарантированно рабочий релиз.

### 16.3. Экран применения

До запуска пользователь видит подготовленный diff, план затрагиваемых компонентов, обращения к данным, точку возврата и возможный перерыв доступности. Подтверждение относится к показанной ревизии плана.

Во время операции отображаются этап, время, журнал, очередь и доступные безопасные действия. Процент выполнения показывается только для измеряемых шагов; неопределённая длительность Docker build не заменяется вымышленным процентом.

После операции сохраняются результат и ссылка на историю. Закрытие страницы не отменяет работу executor.

Для Stop и других действий с перерывом доступности предусматривается понятное подтверждение цели. Повторные подтверждения одного неизменённого плана не требуются.

### 16.4. Экран восстановления

Пользователь видит фактическое состояние, последний подтверждённый этап, сохранённые recovery points и доступные варианты. Неопределённый результат обозначается `Requires recovery`; он не скрывается общим сообщением `Build failed`.

Веб-интерфейс не предлагает выполнить неподдерживаемое восстановление данных. При недоступном web документация указывает эквивалентный CLI-сценарий.

## 17. Ограничения ресурсов и эксплуатационные требования

### 17.1. Настройки по умолчанию

| Параметр | Начальное значение |
|---|---|
| Одновременные Docker build | 1 |
| Одновременные операции копирования | 1 |
| Одновременные переключения | 1 на хост; увеличение доступно после отдельной проверки |
| Интервал метрик | 5 секунд |
| История метрик MVP | 60 минут |
| Предыдущие проверенные релизы | 3, с дополнительными защищёнными объектами по §11 |
| Ручные снимки | 3 |
| Максимальная отображаемая запись лога | 64 KiB, с явной отметкой усечения |
| Буфер потока на клиента | 1 MiB, далее контролируемое отбрасывание с отметкой |
| Общий бюджет журналов операций | 200 MiB, с защитой активных журналов и минимальных итоговых событий |
| Подробный вывод одной операции | 20 MiB, далее явное усечение/ротация; критические события этапов сохраняются отдельно |

Квоты снимков, staging и Docker-артефактов задаются при настройке после оценки размера сервисов. Минимальный свободный резерв должен учитывать одновременно recovery point, кандидат и ожидаемую сборку. Размер build cache не определяется только размером исходников и контролируется отдельно.

Лимиты и таймауты имеют проверку диапазонов. Панель не должна при нехватке места удалять защищённые точки возврата ради продолжения обновления.

### 17.2. Ресурсы самой панели

Dashboard и executor запускаются с настраиваемыми Compose/cgroup ограничениями CPU, памяти, числа процессов и I/O там, где это поддерживается средой.

Ограничения контейнеров — верхние пределы, а не резервирование или гарантия наличия RAM. Их сумма не доказывает, что на хосте поместятся панель, ОС, Docker, BuildKit и игровые приложения. В текущем Compose заданы пределы 256 MiB для dashboard и 384 MiB для executor; это не измеренное постоянное потребление и не бюджет всей VM. В отчёте фиксируются фактически применённые лимиты, включая tmpfs и число процессов.

Лимиты процессов панели не считаются лимитами Docker daemon или BuildKit. Нагрузка сборок контролируется очередью, зарегистрированными настройками builder и проверкой давления на ресурсы. При нехватке ресурсов новые тяжёлые задачи не запускаются; доступ к состоянию и восстановлению должен сохраняться. На `competition-4g` проверяется реальная доступная память, а не только объявленные 4 GiB: в выбранной VM swap отсутствует и часть RAM зарезервирована ядром.

Метрики и live-потоки используют ограниченные очереди. Заполнение очереди телеметрии не блокирует журнал критических шагов и не должно останавливать игровые сервисы.

### 17.3. Проверяемые цели производительности

Испытания различают два профиля. Результат одного профиля не переносится на другой.

| Профиль | Среда и назначение | Условие приёмки |
|---|---|---|
| `competition-4g` | Выбранный пользователем обязательный профиль соревнований: выделенная Linux/amd64 VM, 4 vCPU, 4 GiB RAM гостя, виртуальный диск 40 GiB | Отдельный прогон на этом профиле с записью фактической usable RAM, swap, свободного места и inode; физический NVMe не является подтверждённым свойством доступного стенда |
| `legacy-8g` | Исторический опорный benchmark: Linux/amd64 VM, 4 vCPU, 8 GiB RAM, локальный SSD | Сохраняется для сопоставления прежних целей и отчётов; не заменяет `competition-4g` и не требуется вместо него для соревнований |

В `competition-4g` объём назначенной гостю памяти и доступный Linux объём учитываются раздельно. На выбранной VM `lsmem` подтверждает online ranges суммарно 4 GiB, тогда как `MemTotal` составляет около 3,318 GiB; при наличии этих независимых наблюдений профиль допускает usable RAM от 3 GiB. Отсутствующий объём нельзя считать доступным для приложений или компенсировать только заявлением о настройках VM. Без подтверждённого объёма online memory соответствие профилю не выводится из уменьшенного `MemTotal`. Прогон с другой конфигурацией crashkernel/swap записывается с новыми условиями и не подменяет исходный результат.

Нагрузочный сценарий каждого профиля использует 5 синтетических сервисов и 10 контейнеров с фиксированными ресурсами и данными. Это ограниченная воспроизводимая нагрузка; она не доказывает, что любые пять CTF-сервисов поместятся на 4 GiB. Набор реальных сервисов соревнования требует отдельного измерения с их БД, кешами, игровыми данными и сборками.

Отчёт содержит выбранный profile ID, версии дистрибутива/ядра/Docker/Compose, архитектуру исполняемого бинарника и daemon, выделенность стенда, число CPU, online memory и источник наблюдения, `MemTotal`/`MemAvailable`, резерв crashkernel, swap, номинальный размер виртуального диска, ёмкость и свободные байты/inode используемых файловых систем, образы fixtures и применённые cgroup-лимиты. Номинальные 40 GiB диска не равны свободному месту после установки ОС, образов и кешей. Модель виртуального диска, filesystem capacity или успешный тест не подтверждают физический SSD/NVMe хоста.

Для режима наблюдения без сборок и копирования, с метриками раз в 5 секунд и пятью клиентами логов при суммарном входном потоке до 200 строк по 1 KiB в секунду:

- Суммарный RSS web и executor — не более 256 MiB.
- Среднее потребление CPU за 5 минут — не более 0,1 CPU, то есть 10% одного ядра.
- p95 ответа API состояния — не более 500 мс при двух запросах в секунду на исправном стенде.
- Создание фонового задания возвращает идентификатор не позднее 1 секунды без ожидания освобождения очереди.

Эти цели относятся к панели и проверяются отдельно для `competition-4g` и `legacy-8g`. RSS двух процессов не включает игровые контейнеры, ОС, Docker/containerd, BuildKit, файловый кеш и браузер. Для CPU отчёт указывает способ учёта и накладные расходы healthchecks/сбора. Параллельно фиксируются общая память хоста, OOM/restart и ошибки запросов; прохождение бюджета панели не означает отсутствие давления на всю VM.

На `competition-4g` отдельная серия запускает Prepare/Build/Deploy/Rollback при работающих fixtures и наблюдении: сборка одна, состояние панели остаётся доступным, подтверждённые данные сохраняются, ошибки ресурсов не приводят к ложному успеху. Ресурсы Docker/BuildKit, свободное место и время операций измеряются отдельно. Часовой soak для истории метрик и долговременного потребления ресурсов не заменяется пятиминутным замером CPU/API.

Для эталонного приложения без БД, с готовым локальным образом и прогревом до 5 секунд, быстрый rollback должен завершаться функциональной проверкой за 30 секунд на `competition-4g`; тот же benchmark для `legacy-8g` записывается отдельно. Для остальных сервисов длительности измеряются отдельно, а таймауты задаются в их профилях. Возможность отката без registry подтверждается самостоятельным аварийным сценарием A06.

Инвентаризация выбранной VM и исторические прогоны на общей OrbStack VM не закрывают A27. Прохождение численных целей, функциональной серии и оставшихся обязательных сценариев подтверждается только соответствующими отчётами в [матрице приёмки](progress.md). Физический NVMe и производительность произвольного vulnbox такими отчётами не гарантируются.

## 18. Git-источники MVP и последующие расширения

В мастере регистрации и настройках существующего Git-источника Admin может нажать «Проверить подключение» до сохранения. Executor проверяет URL, HTTPS/TLS, публичный DNS и доступ к репозиторию с введёнными либо подходящими сохранёнными credentials, получает опубликованные refs через `ls-remote` и возвращает ограниченный список веток. Выбор ветки подставляет полный `refs/heads/...`; ручной ref/tag/SHA сохраняется. Доступность репозитория и выбранной версии показывается раздельно: отсутствующий или неоднозначный ref не получает успешного подтверждения, SHA вне advertisement остаётся непроверенным. Подкаталог, тип объекта и содержимое проверяются при Fetch.

Проверка не сохраняет credentials/configuration, не скачивает объекты и не создаёт кандидаты или операции. Нужны Admin, CSRF и актуальная сессия после RPC; аудит не содержит URL, токенов или имён веток. Токен существующего источника используется только при неизменных URL и пользователе, без запроса очистки/замены. Пределы: 20 секунд на проверку, две одновременные проверки на executor-процесс, 512 КиБ stdout, 8192 записи refs и до 256 веток в ответе с явным усечением. Действуют те же запреты private-network/SSH/redirect/ambient proxy и те же изоляция Git и TLS, что при Fetch. Изменение формы, токена, сервиса или новый запрос инвалидируют старое подтверждение; проверка остаётся необязательной перед сохранением.

### 18.1. Generic Git — входит в MVP

Основной механизм MVP — Git CLI по зарегистрированному HTTPS URL с необязательным read-only токеном минимальных прав. Поддерживаются GitHub, GitLab, в том числе собственный GitLab на публичном IP с доверенным TLS-сертификатом, и совместимые Git-серверы. API провайдера не требуется. SSH, deploy keys, GitLab во внутренней сети, polling и webhooks остаются последующими расширениями.

Admin задаёт URL, ref (branch/tag/точный SHA), необязательный подкаталог репозитория и credentials через панель. Токен вводится в поле пароля, не возвращается API, не сохраняется в браузере и не передаётся в URL или argv. Повторное сохранение без нового токена имеет явную семантику сохранения/удаления credential; секретные значения хранятся в vault. URL со встроенными credentials, локальные пути, file/ssh/ext и произвольные transport helpers отклоняются.

Ручное действие `fetch_source` проходит Preview → подтверждение → долговечная операция с locks, таймаутом и журналом. Defender может получить кандидат из уже настроенного источника; менять URL/credentials может только Admin. После загрузки UI показывает точный SHA, diff и подготовленный кандидат. Настройка источника и получение кандидата сами по себе не выполняют Build или Deploy.

Обязательные правила:

- Checkout находится вне игровых каталогов и выполняется без root.
- В MVP разрешён только HTTPS с проверкой TLS; редиректы и дополнительные transport protocols запрещены. SSH host keys относятся к следующему SSH-профилю.
- Конфигурация Git и credentials из игрового `.git` не используются.
- Hooks и произвольные transport helpers не выполняются; submodules, filters и LFS отсутствуют в первом Git-профиле либо включаются отдельной проверенной политикой.
- На загрузку действуют ограничения: 120 секунд, 64 MiB локальных Git-объектов, 32 MiB экспортированного дерева, 16 MiB одного файла и 20 000 файлов. Предел файла допускает поставляемые CTF-бинарники и SQLite amalgamation при сохранении общего бюджета. Недоверенный Git-процесс не получает Docker socket, vault, IPC или активные игровые mounts; права UID/GID сбрасываются перед запуском Git.
- Изменения привязываются к точному SHA; перемещение ветки после подготовки не меняет кандидат.
- Все исходники проходят тот же staging/build/deploy pipeline, что и локальный источник MVP.

Первый режим Git — создание полного неизменяемого кандидата явно управляемого дерева из выбранного коммита; отсутствие файла означает удаление только внутри этого дерева при последующем Deploy. Локальный workspace при загрузке не перезаписывается. Секреты и постоянные данные не становятся управляемыми автоматически. Symlinks, special files и неподдерживаемые gitlinks блокируют публикацию кандидата; `.git` и credentials в него не включаются. Ошибка сети/авторизации/лимита оставляет активный сервис и ранее подготовленный кандидат без изменений. Откат продолжает работать без Git или сети.

### 18.2. Overlay

Overlay вводится после полного режима и должен иметь отдельный формат пакета исправлений: идентификатор основы, управляемые пути, добавления/изменения, явные удаления и правила конфликтов.

Отсутствие файла в Overlay-репозитории само по себе не означает удаление из сервиса. Повторное применение одного пакета к той же основе должно давать тот же итоговый хеш. Несовпадение ожидаемой основы останавливает применение до разрешения конфликта.

### 18.3. Проверка обновлений и автоматизация

Polling работает независимо от входящих подключений. Webhooks допускаются при наличии безопасного канала, проверке подлинности, защите от повторной обработки и сопоставлении события с зарегистрированным репозиторием. Панель управления не должна становиться публичной ради webhook.

Auto Deploy выключен по умолчанию. Его включение требует определённой политики источника, проверок, совместимости данных и отката. Webhook запускает получение и проверку кандидата, а не передаёт команды executor.

### 18.4. Работа без внешней сети

MVP обеспечивает автономный возврат уже сохранённых релизов. Последующий экспорт/импорт релизов позволяет заранее перенести образы и артефакты для новых развёртываний.

Импортируемый пакет считается недоверенным: проверяются состав, пути, размеры, хеши и соответствие локальной политике. Политики хоста и секреты не заменяются импортом автоматически.

### 18.5. Групповые контрольные точки

Backup All создаёт набор снимков с общим идентификатором и временем начала/окончания. Последовательные снимки разных сервисов не объявляются атомарной контрольной точкой всей инфраструктуры.

Параллелизм ограничивается отдельно. Восстановление выполняется по сервисам с учётом их зависимостей, а не безусловным откатом всех игровых данных.

### 18.6. Информация соревнования

Можно добавить название события, начало, длительность раунда, TTL флага и временные метки раундов на графиках. Эти сведения носят информационный характер и не заменяют расписание организаторов.

Интеграция внешнего checker должна показывать источник, время и актуальность результата отдельно от локального healthcheck. Автоматические действия на её основе вводятся отдельной политикой.

### 18.7. Сырые пакеты TCP/UDP, потоки и gRPC

**Статус: TCP/UDP packets/PCAP, TCP-потоки, gRPC/descriptors и HTTP/2 termination реализованы; Linux/VM-приёмка отложена.** Поддерживаемые bounded профили, доступ и ограничения: [traffic-analysis.md](traffic-analysis.md). Контракты, этап 10 и матрица C01–C10: [packet-capture-plan.md](packet-capture-plan.md).

Пассивный capture работает отдельно от HTTP Proxy, наблюдает только разрешённый трафик зарегистрированных сервисов и не требует переноса их портов. Фильтры — сервис/компонент, TCP/UDP, IP/порты, время и направление. Реализованы hex/ASCII, classic PCAP, bounded TCP reassembly, UDP datagrams и HTTP/2/gRPC decoder. PCAPNG и дополнительные декодеры остаются поздними расширениями. Переключение представления не меняет маршрутизацию и не добавляет произвольный TCP/UDP в текущий HTTP Proxy.

Обязательны отдельные лимиты CPU/RAM/диска, ротация, bounded capture/reassembly, счётчики потерь и исключение административного/постороннего трафика. Сопоставление учитывает Docker NAT/bridge/veth/loopback, runtime epochs и две стороны proxy; дубли/неоднозначность не скрываются. Capture и архив изолированы от Docker socket, vault, игровых mounts и основного IPC. Текущая упаковка выдаёт capture только CAP_NET_RAW; runtime-подтверждение прав Linux отложено. Профиль предлагает до 8 проверенных bridge-сетей компонента, bridge-member veth и host-publication альтернативы с точными name/index; canonical leg не позволяет одновременно включить container и host сторону одного target. Host management ports защищены, custom protected ports задаёт root. Linux/NAT runtime-приёмка остаётся открытой. Lease 10 секунд обновляется единственным worker каждые 2 секунды после сверки runtime; операции смены runtime и компенсации предварительно приостанавливают наблюдение. Начальное сохранение bytes выключено, Admin выбирает snaplen явно. [Установка и ограничения](packet-capture-deployment.md).

Raw payload/PCAP может содержать неотредактированные игровые секреты: просмотр и экспорт требуют sensitive access и аудита, настройка — Admin. gRPC требует HTTP/2 и gRPC framing, а осмысленные имена protobuf-полей — подходящих descriptors. TLS остаётся шифрованным без отдельного принятого механизма termination/session secrets; профиль `https1` не меняется автоматически: для TLS HTTP2/gRPC включается `https2` → h2c с отдельным preflight/capture, как описано в [traffic-analysis.md](traffic-analysis.md). Пассивный capture не применяет HTTP WAF к TCP/UDP; сетевые ограничения планируются отдельно.

### 18.8. HTTP reverse proxy, страница трафика и базовый WAF

**Статус: HTTP/1.1, групповой перенос/возврат, TLS и отдельный HTTPS/2→h2c профиль реализованы; соревновательная приёмка отложена.** По решению пользователя 30 октября разработка продолжена при отложенной приёмке нестабильной VM. Подробные контракты, ограничения текущего профиля и матрица P01–P16: [http-proxy-waf-plan.md](http-proxy-waf-plan.md). Установка: [http-proxy-install.md](http-proxy-install.md).

Порядок работ обновлён пользователем: сейчас реализовать proxy, страницу трафика и WAF, затем вернуться к общей приёмке на стабильном `competition-4g`. Незавершённые проверки MVP остаются открытыми. Их CPU/RAM/диск учитываются сверх бюджета двух контейнеров панели из §17.3; прежние результаты MVP не подтверждают вместимость VM или overhead после подключения proxy. Численные лимиты нового модуля фиксируются по результатам прототипа и проверяются на том же соревновательном профиле до переноса игровых портов.

Admin подключает proxy к зарегистрированному сервису и подтверждает маршрут `внешний IP:порт → внутренний компонент:порт`. Уже занятый сервисом порт переносится только отдельным планом с показом сетей/bindings, пересоздаваемых application-контейнеров, сохранением игровых данных и процедурой возврата. Произвольный upstream из запроса клиента не принимается. Обычная установка MVP и Deploy кода не меняют сеть ради proxy.

В панели вводятся страницы «Трафик» и «Proxy / WAF». Первая показывает весь сохранённый HTTP-трафик подключённых маршрутов: запросы и ответы, service/route/request ID, время, IP, метод/URL, статус, длительность, объёмы, решение WAF и доступные headers/body. Обязательны режим «Все сервисы», фильтр по сервисам, времени/IP/методу/status/WAF, live/pause, cursor pagination и карточка обмена. «Весь» относится к проходящим через proxy маршрутам и ограниченному окну хранения; потери, отключённый body capture и усечение не скрываются.

Proxy и recorder работают в отдельном opt-in Compose-проекте без Docker socket, executor IPC и игровых файловых mounts. Остановка dashboard/executor не прекращает маршрутизацию на последней подтверждённой политике. Хранилище/очередь/тела ограничены; отказ записи не задерживает пересылку. Просмотр payload требует sensitive_access, значения секретных headers и настроенных полей редактируются до записи. Недоверенный HTML/JS не выполняется в панели.

Текущий профиль — HTTP/1.1 на свободных портах либо подтверждённый групповой перенос всех явных TCP-публикаций application-компонентов одного сервиса. Каждая пара «application-компонент + контейнерный TCP-порт» получает отдельный разрешённый loopback backend. План включает до 8 компонентов, 16 таких пар и 32 внешних привязок, полностью покрывает публикации приложения и не переносит БД/служебные зависимости. Все порты компонента меняются одним его пересозданием; шаги нескольких компонентов выполняются последовательно с долговечной фиксацией намерения и результата каждого шага. Отдельный runtime overlay сохраняет маршрутизацию при Deploy/Rollback, возврат портов оставляет текущий релиз и данные. В смешанном состоянии каждый компонент сверяется с исходными либо закрытыми привязками независимо. При неизвестном образе/mount/runtime, пропавшей зависимости или чужой политике выставляется requires_recovery без слепого повторения Compose. Отсутствующие application-компоненты восстанавливаются только по однозначной сохранённой опоре. Старые однокомпонентные записи поддерживаются без переписывания их digest. Engine использует стандартный Go `net/http` / `httputil.ReverseProxy`, поддерживает streaming/SSE и WebSocket handshake. TLS termination использует immutable ID профиля, TLS 1.2+, HTTP/1.1 ALPN, SAN/SNI/сроки цепочки и отдельный read-only каталог ключей. Upstream остаётся loopback HTTP; повторный TLS и ACME пока не реализованы. HTTP/2/gRPC поддерживается отдельным `https2` профилем с h2c backend (§18.7), без смены правил `http1/https1`. Содержимое TLS passthrough, WebSocket frames и произвольный TCP/UDP остаются отдельными профилями. Сохранность HTTP-семантики и совместимость конкретного CTF checker подтверждаются до переноса порта.

Первый WAF предоставляет per-service per-IP rate limit/burst, режимы off/observe_only/enforce, HTTP 429/Retry-After при превышении, временный autoban после N нарушений за окно, список/снятие банов и явные checker exceptions. Новый маршрут запускается в observe_only. IP берётся из TCP peer либо строго настроенной trusted proxy chain, без слепого доверия X-Forwarded-For/Forwarded. NAT, bounded IP state, TTL, переполнение и аварийное отключение имеют явную политику. Сигнатурный WAF и volumetric DDoS protection не обещаются первым выпуском.

Изменения политики проходят preview/digest, атомарную активацию и observed revision. Неверная конфигурация сохраняет last-known-good. Отказ самого proxy не равен отказу страницы трафика: возврат прямых портов выполняется по отдельному сохранённому плану, автоматический обход не предполагается. Перед enforce обязательны проверка checker и приёмка observe-only на целевом профиле.

## 19. Этапы разработки

Сроки оцениваются после этапа 0 и прототипа импорта Compose. Последовательность определяется зависимостями и проверяемыми результатами, а не календарными обещаниями.

### Этап 0. Контракты, профиль Compose и тестовый стенд

**Работы:** зафиксировать поддерживаемый профиль Compose, модель угроз, форматы Service/Snapshot/Release/Operation, карту данных, протокол executor и схему двух контейнеров панели с совпадающими host-путями. Подготовить тестовые проекты: приложение с БД и named volume, приложение с bind-mounted кодом и данными, несовместимый проект с данными в writable layer.

**Результат:** архитектурные решения, схемы данных, матрица совместимости и воспроизводимый стенд с API записи/чтения тестового флага.

**Выходной критерий:** для каждого тестового проекта однозначно определены управляемые файлы, сохраняемые данные, цели переключения и поддерживаемость. Стенд работает независимо от панели.

### Этап 1. Локальный executor и безопасная регистрация

**Работы:** каркас Go, разделение UID dashboard/executor, Dockerfile runtime-образов, Compose, bootstrap каталогов/IPC и разрешённых корней, доверенный реестр, локальный административный CLI, preflight, чтение Docker, нормализация Compose и регистрация с подтверждением политики. Добавить структурированные журналы с первого этапа.

**Результат:** CLI показывает фактическое состояние и формирует доверенную регистрацию существующего проекта.

**Выходной критерий:** регистрация не меняет контейнеры; project name и хранилища сохранены; неподдерживаемые и конфликтующие проекты отклоняются; пути вне разрешённых корней и произвольные команды не принимаются. Executor работает в Linux-контейнере, принимает разрешённый UID через IPC; dashboard не видит Docker socket и его приватные данные.

### Этап 2. Очередь операций и аварийная сверка

**Работы:** долговечный журнал, ключи идемпотентности, блокировки общих ресурсов, состояния операций, таймауты и обработка потери Docker API. Реализовать механизм fault injection для интеграционных тестов.

**Результат:** единый движок выполнения для CLI и будущего web.

**Выходной критерий:** повтор запроса создаёт одну операцию; конфликтующие действия не выполняются параллельно; после остановки процесса незавершённая операция определяется и проверяется без слепого повтора.

### Этап 3. Снимки, сохранение образов и ручной возврат

**Работы:** baseline, manifest, проверка целостности, импорт первоначального релиза, удержание образов, recovery points, раздельная ротация и предварительный расчёт места. Реализовать возврат сохранённого релиза через CLI на тестовом стенде.

**Результат:** проверяемая точка возврата существует до разработки полноценного обновления.

**Выходной критерий:** восстановление использует сохранённые файлы/образы и прежние хранилища; сетевой доступ отключён; игровые данные читаются после возврата; ротация не удаляет защищённые объекты.

### Этап 4. Полный pipeline Deploy

**Работы:** изолированный staging, diff, проверка ревизий и drift, сборка уникальных образов, подготовленный Release, план переключения, применение файлов, прогрев и локальные проверки. Добавить подробные журналы и безопасную отмену.

**Результат:** ручной цикл Prepare → Build → Deploy → Rollback работает через CLI и внутренний API executor.

**Выходной критерий:** ошибки до переключения не меняют активный экземпляр; успешное обновление сохраняет данные; bind mounts и зависимости обрабатываются по профилю; сбои после переключения дают проверенный результат или `requires_recovery`.

### Этап 5. Web, авторизация и командная работа

**Работы:** непривилегированный dashboard-контейнер, отдельная БД, локальный bootstrap первого администратора, пользователи, сессии, RBAC, CSRF/Origin, встроенный frontend и WebSocket. Подключить Dashboard, карточки сервисов, diff, операции, релизы, снимки и live-логи. Реализовать мастер регистрации по пути, просмотр заявки и подтверждение Admin через панель, автоматическую инициализацию source workspace/baseline и повтор после ошибки инициализации. Добавить настройку HTTPS Git URL/ref/credentials и долговечное получение кандидата с точным SHA через общий pipeline.

**Результат:** повседневные действия доступны команде через защищённый интерфейс.

**Выходной критерий:** сервис добавляется и подтверждается без CLI внутри заранее подключённых корней; неподдерживаемые/конфликтующие проекты блокируются без изменения игры. Все изменяющие HTTP/WebSocket пути защищены; регистрация и настройки Git доступны только Admin, Viewer не запускает операции; web UID не расширяет bootstrap-корни/привилегии executor. Получение Git-кандидата сохраняет точный SHA, не изменяет active/data и не раскрывает токен; повторное нажатие и закрытие вкладки не дублируют и не отменяют операцию. До готовности авторизации изменяющий web API не включается.

### Этап 6. Метрики, установка и эксплуатация

**Работы:** базовые метрики с проверенными источниками внутри контейнерной схемы, лимиты потоков, квоты и очистка, проверка Compose bootstrap/healthchecks, согласованный экспорт БД/конфигурации, обновление образов панели и документация аварийного CLI через `docker compose exec executor`. Проверить IPC после аварийного завершения и независимость игровых проектов от установки/остановки панели.

**Результат:** панель устанавливается и обслуживается без вмешательства в жизненный цикл игровых сервисов.

**Выходной критерий:** установка/перезапуск/обновление панели не перезапускают игровые контейнеры; восстановление работает без web; цели ресурсов проверены на выбранном профиле `competition-4g` с условиями и ограничениями §17.3.

### Этап 7. Приёмка MVP

**Работы:** прогнать матрицу §20 на Linux/amd64 `competition-4g`, испытания аварийных завершений на каждом изменяющем шаге, нагрузку логов, отключение сети и имитацию нескольких раундов с записью/чтением флагов. Зафиксировать условия VM, выполнить наблюдение и отдельную серию операций под нагрузкой по §17.3; не переносить результаты `legacy-8g` или общей OrbStack VM на этот профиль.

**Результат:** выпуск MVP с двумя образами, Dockerfile/Compose/bootstrap, встроенным frontend, аварийным CLI, матрицей совместимости, инструкциями и отчётом проверок.

**Выходной критерий:** все обязательные сценарии пройдены в заявленном профиле и отражены в матрице приёмки; для каждого заявленного профиля данных подтверждено сохранение состояния; отсутствуют открытые дефекты, приводящие к потере данных, расширению привилегий или ложному успеху операции. До выполнения критерия MVP не объявляется принятым, этап 9 не начинается.

### Этап 8. Расширенные источники и дальнейшие возможности

После HTTPS Generic Git из MVP реализуются SSH-профиль, polling, формализованный Overlay и перенос релизов. API провайдеров, webhooks, автоматизация и трафик добавляются самостоятельными выпусками с отдельными критериями приёмки. Новый источник кандидата не создаёт второй pipeline применения.

### Этап 9. HTTP Proxy, наблюдение трафика и базовый WAF

**Работы:** 9.0 — контракт/прототип engine и совместимости; 9.1 — отдельный Compose proxy, маршруты и безопасный перенос/возврат внешних портов; 9.2 — capture/recorder и страница «Трафик» с общим журналом/фильтрами сервисов; 9.3 — trusted IP и WAF observe-only; 9.4 — per-IP enforcement, autoban TTL, исключения и управление; 9.5 — аварийная/нагрузочная приёмка P01–P16.

**Результат:** команда управляет HTTP-входом сервисов, просматривает проходящие запросы/ответы и явно включает ограничения злоупотребления частотой, сохраняя работоспособность checker и игровых данных.

**Выходной критерий:** маршрут и возврат подтверждены на реальном HTTP-сервисе; фильтры различают сервисы; rate/burst/ban не обходятся подменой IP headers; потери capture и отказ панели не блокируют пересылку; ошибка policy сохраняет рабочую версию, local recovery доступен. Численные цели overhead фиксируются прототипом, затем проверяются под нагрузкой. Матрица P01–P16 ведётся отдельно от A01–A39.

По решению пользователя 30 октября этап выполняется параллельно отложенной приёмке MVP; Git/Overlay-расширения этапа 8 не являются условием. Реализованы свободные маршруты, групповой перенос/возврат занятых портов нескольких application-компонентов и TCP-портов одного сервиса, TLS termination, независимые proxy/recorder, трафик, bounded capture/WAF и аварийный CLI. P02/P16 имеют локальные свидетельства, но реальный Docker/CTF цикл, совместимость checker и нагрузочная приёмка P15 остаются открытыми. Proxy не включается автоматически при обычном запуске панели. Его расход ресурсов проверяется сверх прежнего бюджета MVP; local race/API/socket tests не заменяют Linux/amd64 Compose-прогон.

### Этап 10. Пакетный захват и декодирование протоколов

**Работы:** 10.0 — Linux prototype/границы ресурсов и карта сервисов; 10.1 — TCP/UDP packets, фильтры и PCAP export; 10.2 — bounded TCP streams/UDP datagrams; 10.3 — plaintext HTTP/2/gRPC и descriptors; 10.4 — отдельный TLS visibility профиль; 10.5 — изоляция, аварии, нагрузка и реальные checker. [Матрица C01–C10](packet-capture-plan.md).

**Выходной критерий:** наблюдение нескольких протоколов не вмешивается в игровые соединения; фильтры и provenance корректны, секретные данные защищены, неполнота записи/декодирования явна, ресурсный бюджет проверен. Статус — разработка 10.0–10.4 завершена в объявленных capture/streams/gRPC/termination профилях и проверена локально; измеренный Linux resource budget и приёмка 10.5 открыты. VM-испытания отложены пользователем; C-критерии не закрывают A/P-матрицы.

## 20. Критерии приёмки MVP

Все проверки выполняются на воспроизводимом Linux-стенде; обязательный соревновательный профиль — Linux/amd64 `competition-4g` (§17.3). Используются только тестовые флаги и данные. Результаты фиксируются для поддерживаемых версий Docker/Compose и каждого заявленного профиля хранилищ. Исторические результаты `legacy-8g`, arm64, эмуляции и общей OrbStack VM сохраняют свои ограничения и не заменяют этот прогон. | A36 | Compose на неподготовленном хосте или новый неразрешённый root | Запуск/регистрация завершаются явной ошибкой; права игровых проектов не меняются; полный rootfs не монтируется |
| A37 | Добавление по пути, просмотр и подтверждение через веб; повтор подтверждения | Admin регистрирует существующий проект без CLI; workspace/baseline готовы либо видна отдельная ошибка инициализации; повтор не дублирует сервис; IDs/StartedAt/данные игры сохранены |
| A38 | Git URL, ref и получение кандидата; ветка затем перемещена или сеть недоступна | Кандидат фиксирует точный SHA и управляемый набор; active/workspace/data не меняются; Build использует зафиксированный кандидат; ошибка сети/ref/проверки лимита до публикации не заменяет предыдущий кандидат; rollback не требует Git |
| A39 | Defender/Viewer регистрирует сервис или меняет URL/credentials; недопустимый Git transport/путь/содержимое | Отказ до регистрации/загрузки; разрешённый fetch доступен Defender, Viewer запрещён; токен не возвращается и не попадает в argv/аудит/снимки; Git выполняется без root и не исполняет hooks/filters/submodules |

Проверка A14 должна быть параметризованной серией испытаний, а не единственным завершением процесса во время сборки. Проверка A03 повторяется для всех вариантов постоянных хранилищ, заявленных поддерживаемыми.

## 21. Организация реализации и результаты поставки

Рекомендуемая структура:

```text
cmd/ctf-manager/          режимы dashboard, executor, init-admin и CLI
internal/domain/         Service, Snapshot, Release, Operation
internal/executor/       протокол и выполнение допустимых действий
internal/policy/         доверенный реестр и проверка планов
internal/jobs/           очередь, блокировки и сверка
internal/docker/         Engine API, Compose adapter, inventory
internal/sourcegit/      изолированное получение HTTPS Git и экспорт blobs
internal/filesystem/     безопасные операции в зарегистрированных корнях
internal/snapshots/      manifest, копирование, целостность
internal/releases/       подготовка, артефакты, применение, возврат
internal/auth/           пользователи и сессии
internal/api/            HTTP и WebSocket
internal/logs/           потоки и журналы операций
internal/monitoring/     метрики и ограниченная история
internal/audit/          события и инициаторы
internal/git/            после MVP
internal/proxy/          opt-in HTTP/1.1 engine, политика WAF, LKG и control API
internal/traffic/        отдельный ограниченный recorder и query API
cmd/ctfm-proxy/          независимый proxy и аварийный CLI
cmd/ctfm-traffic/        отдельный процесс recorder
web/                     React frontend
migrations/              отдельные схемы web и executor
packaging/               конфигурации и профили контейнерной установки
Dockerfile               стадии frontend/build/dashboard/executor
compose.yaml             два сервиса панели
compose.proxy.yaml       отдельный opt-in проект proxy и recorder
Dockerfile.proxy         runtime образы proxy и recorder
scripts/proxy-bootstrap.py bootstrap без изменения игровых портов
scripts/compose-bootstrap.py root bootstrap каталогов и approved mounts
tests/fixtures/          тестовые Compose-проекты
tests/integration/       сценарии приёмки и fault injection
docs/                    ТЗ, установка, эксплуатация, восстановление
```

Снимки, релизы и операции не зависят от HTTP-обработчиков. Веб-панель и CLI используют один прикладной движок executor. Работа с Docker и файловой системой отделена адаптерами, но гарантии сохранения данных проверяются интеграционно с реальным Docker.

Поставка MVP включает:

1. Исходный код и воспроизводимый процесс сборки бинарника с frontend.
2. Runtime-образы dashboard и executor для обязательной целевой архитектуры; нативный бинарник для диагностики.
3. Dockerfile, Compose, локальный bootstrap и примеры конфигурации с явными approved roots.
4. Матрицу совместимости и точный профиль Compose.
5. Инструкции регистрации, подготовки, применения, возврата и обновления панели.
6. Порядок действий при потере web/executor/Docker и при исчерпании диска.
7. Документированные ограничения хранения данных, секретов и миграций БД.
8. Тестовые сервисы и отчёт прохождения обязательной приёмки.

## 22. Технические основания

Следующие первичные источники поясняют ограничения, учтённые в требованиях. Они не заменяют матрицу совместимости конкретного выпуска.

- [Docker Compose services](https://docs.docker.com/reference/compose-file/services/) — права, healthchecks, UID/GID, read-only и bind mounts контейнеров панели.
- [Official Docker CLI image](https://hub.docker.com/_/docker) — CLI/Compose/Buildx в executor без вложенного daemon.
- [Docker Engine security](https://docs.docker.com/engine/security/) — полномочия Docker daemon и проверка входных параметров.
- [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/) — связь файлов хоста с работающими контейнерами.
- [Docker storage](https://docs.docker.com/engine/storage/) — writable layer, volumes, bind mounts и tmpfs.
- [Docker Compose config](https://docs.docker.com/reference/cli/docker/compose/config/) — объединение и нормализация конфигурации.
- [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/) — создание и пересоздание контейнеров.
- [Docker Compose restart](https://docs.docker.com/reference/cli/docker/compose/restart/) — перезапуск существующих контейнеров.
- [SQLite Online Backup API](https://www.sqlite.org/backup.html) — согласованное резервирование работающей БД.
- [SQLite WAL](https://www.sqlite.org/wal.html) — особенности выбранного режима хранения метаданных.
