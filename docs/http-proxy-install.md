# Установка HTTP Proxy и журнала трафика

Профиль рассчитан на Linux, зарегистрированные HTTP-приложения и фиксированные TCP-публикации. Можно подключить свободный порт либо подтвердить перенос всех существующих TCP-публикаций application-компонентов одного сервиса. Поддерживается TLS termination. Для HTTP/2/gRPC добавлен отдельный `https2` → h2c профиль. Для другого TCP/UDP доступны отдельные режимы просмотра пакетов и потоков. TLS passthrough inspection и повторное TLS до upstream не добавлены. Проверки на VM отложены пользователем; локальные результаты не подтверждают capacity соревнований.

`traffic-proxy` и `traffic-store` запускаются независимым Compose-проектом. Основная панель и executor сохраняют свою сеть. Управление из executor идёт через отдельные Unix-сокеты с разными учётными данными. Proxy получает собственную политику, собственное состояние и токены control/ingest; recorder — только свой архив и токены ingest/read. Docker socket, IPC executor и игровые файлы им не нужны.

## Подготовка

На выделенном Linux-хосте, из каталога репозитория:

```sh
sudo python3 scripts/proxy-bootstrap.py --root /srv/ctfm-proxy
```

Команда создаёт **новый** каталог и отказывает при существующей установке. Файлы основной панели, сервисы и их порты она не меняет. Генерируются:

- пустая политика `policy/policy.json` без игровых listeners;
- отдельные каталоги состояния и control-сокетов для UID 10002/10003, пустой root:GID10002 каталог TLS с режимом 0750;
- три случайных credentials с приватными копиями для каждого разрешённого UID; значения не печатаются;
- `executor-proxy.json` — фрагмент bootstrap-конфигурации executor для проверки и объединения с действующим `executor.json`;
- `executor-proxy.override.yaml` — дополнительные mounts только для executor;
- `compose.env` для отдельного проекта proxy.

Диапазон внешних портов по умолчанию — 19080–19111. Закрытые backend-порты по умолчанию — 29080–29111, отдельный диапазон задаётся `--backend-port-min` / `--backend-port-max`. Разрешённые bind IP по умолчанию — `0.0.0.0` и `127.0.0.1`; маршрут выбирается и подтверждается через панель. Другие адреса/диапазон задаются флагами `--listen-ip`, `--port-min`, `--port-max` при подготовке.

Для игровых портов за пределами диапазона задайте точные пары через `--listen-endpoint 0.0.0.0:8070 --listen-endpoint '[::]:8070'`. В действующей установке внесите эти строки в массив `proxy.allowed_listen_endpoints` в `executor.json` и перезапустите executor. Точная пара разрешает только этот IP с этим портом. Сокет появится только после подтверждения маршрута или переноса.

## Сборка и подключение

Образы основной панели должны быть собраны из версии с Proxy/WAF API и страницами интерфейса. Отдельные образы data plane собираются так:

```sh
sudo docker compose --env-file /srv/ctfm-proxy/compose.env -f compose.proxy.yaml build
sudo docker compose --env-file /srv/ctfm-proxy/compose.env -f compose.proxy.yaml up -d
```

После проверки добавьте поле `proxy` из `/srv/ctfm-proxy/executor-proxy.json` в действующий bootstrap executor. В стандартной установке это `/srv/ctf-manager/config/executor.json`. Остальные поля действующей конфигурации сохраняются.

При запуске основной панели добавьте сгенерированный override к её обычным файлам Compose:

```sh
sudo docker compose --env-file /srv/ctf-manager/config/compose.env \
  -f compose.yaml \
  -f /srv/ctf-manager/config/compose.mounts.yaml \
  -f /srv/ctfm-proxy/executor-proxy.override.yaml \
  up -d --no-deps executor
```

Для следующих пересозданий executor нужен тот же набор файлов. Dashboard не получает control-сокеты, токены или новые файловые mounts. В конфигурации используются `unix:///srv/ctfm-proxy/...` endpoints; network namespace executor остаётся прежним.

После подключения Admin открывает «Proxy / WAF». Для свободного маршрута выбирается проверенная loopback-публикация. Для занятого порта используется отдельный блок переноса, описанный ниже. Новые маршруты начинают в режиме `observe_only`. Для enforcement нужно проверить checker и отдельно подтвердить изменения.

Чтобы добавить тестовый маршрут для сервиса, уже опубликованного на всех IPv4-адресах, администратор хоста может задать `allow_public_backend_observation: true` в разделе `proxy` конфигурации executor и перезапустить executor. В «Proxy / WAF» нажмите «Добавить маршрут», выберите зарегистрированный backend с прямой публикацией, задайте свободный разрешённый адрес на loopback и подтвердите предпросмотр. Такой маршрут использует наблюдение WAF. В журнале появляются запросы, отправленные на адрес прокси. Перед сменой опубликованных портов сервиса или переносом на прокси удалите его тестовые маршруты и дождитесь применения политики.

## Игровой трафик из карточки сервиса

Если у сервиса уже есть внешний адрес для участников или checker, откройте **«Настроить HTTP Proxy» → «Перенести игровые порты»**. Для каждого порта укажите свободный приватный backend-порт. Панель покажет исходные адреса, внутренние порты и изменения контейнеров. После подтверждения прокси принимает HTTP на исходном игровом порту, а приложение доступно на закрытом backend. `0.0.0.0` означает все IPv4-интерфейсы сервера, `[::]` — все IPv6-интерфейсы. Если Docker опубликовал обе привязки, в план входят обе.

Откройте **«Трафик сервиса»** для HTTP-журнала с готовым фильтром. По умолчанию записываются метаданные. Для анализа полезной нагрузки в настройках маршрута есть ограниченная запись поддерживаемых тел запросов и ответов с редактированием чувствительных полей. IP-лимиты начинают в режиме наблюдения. Перед включением блокировки проверьте поведение checker.

Если для сервиса уже есть локальные тестовые маршруты к прямой публикации, сначала удалите их в панели и дождитесь применения плана. Для отключения активного игрового маршрута используйте **«Вернуть прямые порты»**.

## Дополнительный HTTP-маршрут

1. Откройте сервис и нажмите **«Настроить HTTP Proxy»**. В форме выберите существующий простой HTTP-маршрут или добавьте новый.
2. Выберите IP прокси, укажите внешний порт из разрешённого диапазона и выберите внутренний порт из подтверждённых публикаций Docker этого сервиса.
3. Нажмите **«Проверить маршрут»**, проверьте пару адресов в плане и подтвердите применение. Дождитесь подтверждения ревизии прокси.
4. Отправьте HTTP-запрос на адрес прокси и откройте **«Трафик сервиса»**. HTTP-журнал откроется с фильтром по этому сервису.

## Простой лимит запросов

В настройках HTTP Proxy сервиса укажите целое число запросов в секунду на IP. После проверки checker подтвердите план. Прокси считает запросы с одного IP по всем маршрутам сервиса вместе. Например, с лимитом 20 первые 20 запросов за окно в одну секунду проходят. Следующий запрос получает `429` и `Retry-After: 5`. Пока идут эти пять секунд, запросы с того же IP получают `429` с оставшимся временем. Новые запросы не продлевают паузу. После неё IP снова получает полный лимит.

Паузы видны в HTTP-журнале и хранятся только в памяти прокси. Для одного IP, общего у нескольких клиентов за NAT, действует один общий счётчик. Для наблюдения, исключений и управляемых банов можно выбрать расширенные режимы WAF.

При прямой публикации приложения прокси доступен только по разрешённому loopback-адресу. Запросы на прежний прямой порт идут мимо журнала. Если checker должен продолжить обращаться по своему прежнему адресу, а запросы должны попадать в журнал, используйте **«Перенос занятых портов»** на той же странице. Там задаётся новый приватный backend-порт и доступен возврат прямых привязок.

## TLS-профили

В существующей установке после обновления подготовьте отсутствующий каталог `/srv/ctfm-proxy/tls`: root:GID10002, режим 0750. Обновлённый `compose.proxy.yaml` монтирует его только proxy и только read-only; executor/dashboard/recorder этот каталог не получают. Bootstrap новой установки уже создаёт его.

Сертификат и незашифрованный ключ получают у своего CA или из собственной PKI. Ключ на входе импортёра должен иметь режим 0600 или строже. Импорт выполняется локально на Linux-хосте:

```sh
sudo python3 scripts/proxy-tls-import.py \
  --directory /srv/ctfm-proxy/tls --id ctf-2026-01 \
  --certificate /secure/fullchain.pem --private-key /secure/private-key.pem
```

Импортёр проверяет пару, защищённые каталоги и файлы, публикует новый профиль атомарно и не печатает ключ. Proxy проверяет SAN, сроки/подписи цепочки и нужный Host при preview. Профиль с тем же ID не заменяется: обновление сертификата требует нового ID и нового Preview/Confirm. Сохраняйте профили, используемые текущей и предыдущей рабочей политикой, чтобы аварийный возврат не потерял ключ.

В панели выберите HTTPS и профиль сертификата, затем укажите **точное значение HTTP Host**, например `ctf.example.test:18011` для URL `https://ctf.example.test:18011/`. SAN/SNI проверяются по имени без порта. Клиенты должны разрешать это имя на адрес proxy и доверять CA; автоматического отключения проверки доверия нет. Изменение HTTP→HTTPS меняет схему доступа checker, поэтому её и доверие сертификату нужно согласовать до переноса. TLS разрешён с версии 1.2, В `https1` ALPN ограничен HTTP/1.1; в явно выбранном `https2` — h2. TLS keys не загружаются/возвращаются через браузер.

Текущий диапазон внешних портов — 1024–65535; привилегированные 80/443 требуют отдельного профиля прав и сейчас не принимаются. ACME/автопродление и HTTPS до backend пока не реализованы. После termination данные идут на подтверждённый локальный HTTP-порт; трафик в журнале содержит уже расшифрованные и отредактированные HTTP-обмены.

## Перенос занятого порта

Каждая исходная внешняя привязка должна входить в разрешённый диапазон адресов и портов либо в список точных пар. Backend-диапазон задаётся отдельно. При смене владельца порта с Docker на host-network proxy проверьте, что хостовый файрвол пропускает входящий TCP на этот порт.

1. В «Proxy / WAF» выберите сервис. Панель покажет обязательную таблицу всех публикуемых application-компонентов и их контейнерных TCP-портов. Для каждой пары задайте отдельный свободный private backend-порт.
2. Проверьте набор всех прежних внешних привязок и HTTP/HTTPS/capture для каждого target. Политика WAF service scope согласуется для всей группы; route-specific режим выбирается явно. Если target опубликован на разных внешних портах, задайте точный Host отдельно для каждого listener, включая порт. Нельзя оставить альтернативную публикацию того же приложения для обхода WAF.
3. Preview покажет все пересоздаваемые компоненты, их текущие образы/mounts, карту внешних/private bindings, ревизии и перерыв для всей группы. Подтвердите перерыв и сохранение смонтированных данных, затем точный digest. Writable layer пересоздаваемого контейнера не считается постоянным хранилищем.
4. Панель вернёт queued intent и будет показывать этапы. Executor заново проверит runtime, свободный backend-порт и TLS, последовательно пересоздаст выбранные application-компоненты: все порты одного компонента меняются одним пересозданием. После каждого шага сохраняются наблюдаемые ID и состояние привязок, сверяются образы/mounts и незатронутые зависимости. После проверки всей группы применяется proxy. Завершение требует наблюдаемой applied revision и настроенных local checks.

Операция принимает до 8 application-компонентов, 16 пар «компонент + контейнерный TCP-порт» и 32 явных IPv4/IPv6 привязок одного сервиса. Все публикуемые application targets должны присутствовать в плане; backend-порты уникальны и входят в отдельный разрешённый диапазон. UDP, диапазоны, неявные dual-stack bindings и неподдерживаемые layouts блокируются до изменения. Речь о TCP-публикациях HTTP/HTTPS-приложений: произвольные TCP-протоколы не добавляются; gRPC/HTTP2 требуют явного `https2` и успешного h2c probe исходного приложения перед переносом. БД/служебные зависимости и их публикации не переносятся и не защищаются HTTP WAF. Исходный Compose не редактируется. Его runtime overlay применяется executor при последующих Deploy/Rollback/Recover; ручной `docker compose up` по исходному файлу обходит эту политику и создаёт drift, поэтому runtime обслуживается через панель.

## Возврат и незавершённая операция

В истории переноса выберите «Вернуть порты» → новый Preview → подтверждение. Возврат удаляет только маршруты этого переноса, ждёт их applied-удаления/освобождения listener и возвращает группу на исходные привязки с **текущими** релизом, образами и данными. Это не откат версии приложения. Если другой маршрут использует закрытый backend, сначала измените/удалите его: возврат не ломает такой маршрут молча.

При ошибке после изменения executor сверяет известные original/private варианты каждого компонента независимо и выполняет только доказанный компенсирующий возврат всей группы. Смешанная группа фиксируется в журнале; распределённая атомарность Docker не предполагается. Неизвестные контейнеры, образы, mounts, настройки либо чужая политика дают `requires_recovery`; новые задания и подтверждения регистрации остаются заблокированными до нового плана восстановления. После рестарта worker ничего не повторяет автоматически. План отдельно показывает фактически существующие контейнеры и сохранённую опору; каждое отсутствующее приложение восстанавливается только при однозначном подтверждённом образе/хранилищах. Исчезновение незатронутой БД/зависимости требует ручного разбора. Старые однокомпонентные записи возвращаются через тот же flow без переписывания истории.

Если dashboard недоступен, используйте тот же живой executor:

```sh
sudo docker compose --env-file /srv/ctf-manager/config/compose.env exec executor \
  ctf-manager proxy-cutovers
sudo docker compose --env-file /srv/ctf-manager/config/compose.env exec executor \
  ctf-manager proxy-return-preview --cutover CUTOVER_ID
sudo docker compose --env-file /srv/ctf-manager/config/compose.env exec executor \
  ctf-manager proxy-return-confirm --proposal PROPOSAL_ID --digest SHA256_FROM_PREVIEW
```

В нестандартной установке передайте `ctf-manager --config /path/executor.json ...`. CLI использует приватный IPC работающего executor и его единственный worker; второй Manager и обход журнала не создаются. Если executor остановлен, сначала запустите его обычным Compose-набором с прежними mounts. Команда подтверждения возвращает состояние очереди; итог проверяется через `proxy-cutovers`.

## Хранение и ресурсы

Тела по умолчанию не сохраняются. После явного включения ограниченной записи отдельно ограничиваются request/response, редактируются известные чувствительные поля, а неподдерживаемые или неполные форматы получают причину отсутствия тела. Больший пересылаемый поток не обрезается ради архива.

Начальные настройки recorder: окно 60 минут, не более 100 000 записей, общий физический бюджет SQLite и rollback journal 512 MiB, сервисный бюджет 128 MiB. Логический бюджет данных дополнительно ограничен четвертью физического бюджета, оставляя место индексам, страницам и журналу. API отдельно сообщает `stored_bytes`, `payload_budget_bytes`, `disk_bytes` и `quota_bytes`. При понижении квоты ниже существующего файла recorder отказывает, сохраняя архив.

В Compose recorder сохраняет свободный резерв 1 GiB сверх места для своего возможного rollback journal. Если основной executor настроен на больший `storage.minimum_free_bytes` и архив расположен на той же физической файловой системе, увеличьте `--minimum-free-bytes` recorder как минимум до этого значения. Отдельная квота архива не заменяет общий резерв свободного места для критического журнала панели.

В Compose стоят предварительные caps по 256 MiB RAM для каждого контейнера, CPU 1 и 0,5 соответственно. Это ограничения прототипа, а не подтверждённая вместимость соревновательной VM. P15 и совместимость конкретного checker проверяются отдельно.

Recorder работает независимо от основного журнала executor. Потеря записи, заполнение очереди, отказ хранилища и смена epoch видны в счётчиках; отсутствие записей не означает отсутствие запросов. Архив трафика и отдельное состояние proxy не включаются автоматически в backup панели.

## Остановка

Остановка dashboard/executor сохраняет маршрутизацию по последней подтверждённой политике. Остановка recorder прекращает запись и увеличивает счётчики потерь, сохраняя обработку запросов proxy. Остановка самого proxy делает его listener недоступным; автоматический обход на прямые игровые порты не выполняется.

```sh
sudo docker compose --env-file /srv/ctfm-proxy/compose.env -f compose.proxy.yaml stop
```

Каталоги политики, bans/LKG и архива остаются на диске. Данные игровых сервисов находятся вне этого проекта.

## Аварийное управление без панели

На Linux-хосте соберите `make proxy-build`. Следующие команды используют host-пути стандартного bootstrap; для другой установки подставьте её корень. Токен читается из приватного файла, его значение в аргументы не передаётся:

```sh
sudo bin/ctfm-proxy control \
  --unix /srv/ctfm-proxy/proxy-control/proxy.sock \
  --token-file /srv/ctfm-proxy/secrets/executor-control status
```

Чтобы отключить WAF выбранного сервиса с сохранением маршрутизации:

```sh
sudo bin/ctfm-proxy emergency \
  --policy-file /srv/ctfm-proxy/policy/policy.json \
  --state /srv/ctfm-proxy/proxy-state \
  --action disable-waf --service SERVICE_ID \
  --comment 'Причина аварийного отключения'
```

Для возврата предыдущего набора маршрутов и правил используется та же команда с `--action restore-previous`; она публикует его **новой большей ревизией**. Сначала проверьте, какие listeners вернутся: этот возврат не переносит Docker-порты и не восстанавливает игровые данные. Повреждённый desired-файл требует отдельной ручной сверки и не перезаписывается автоматически.

После изменения повторите `control ... status` и проверьте `desired_revision`, `applied_revision` и `last_error`: запись desired-файла сама по себе ещё не подтверждает активацию. Publisher панели сохраняет более новую аварийную политику. При следующем открытии «Proxy / WAF» Admin явно согласует её, затем выполняет свежие Preview/Confirm.

Конкретный временный бан снимается через `control` с флагами `--service SERVICE_ID --ip CLIENT_IP --comment 'Причина' unban`; для route scope добавляется `--route ROUTE_ID`. Список доступен командой `bans`. Все действия управления требуют действующей локальной аутентификации и фиксируются без копирования payload в аудит.

Полный restore основной панели отключает её proxy-подключение и сообщает `proxy_reconfiguration_required`. Независимые proxy/recorder не откатываются вместе с панелью. Перед повторным включением сверяют live desired/applied, текущие сервисы и политики, восстанавливают отдельные credentials/mounts и только затем подключают executor. Архив трафика и bans/LKG имеют отдельную процедуру резервирования.

## HTTP/2 / gRPC и просмотр после TLS termination

В панели выберите `HTTPS · HTTP/2 / gRPC → h2c`, immutable сертификат и точный Host. Backend должен принимать plaintext HTTP/2 prior knowledge: существующий native TLS backend автоматически не расшифровывается и HTTP/1 downgrade не выполняется. Preflight проверяет SETTINGS без вызова application RPC. При переносе порта executor использует только frozen текущие Docker publications, затем проверяет новую private публикацию.

Для сохранения gRPC bodies отдельно выберите `grpc_body`; это неотредактированные framed bytes до 64 KiB на направление, доступные только sensitive-пользователям. По умолчанию остаётся metadata capture. Trailers сохраняются с redaction. WAF ограничивает начала RPC, не отдельные сообщения streaming-вызова. Старые HTTP/1 профили не меняются.

В HTTP detail кнопка разбора показывает gRPC после termination. Для protobuf имён откройте записанный plaintext backend TCP-flow с подходящим version-pinned descriptor. [Подробный контракт и лимиты](traffic-analysis.md). Session keylogs и TLS passthrough decryption этим профилем не включаются.
